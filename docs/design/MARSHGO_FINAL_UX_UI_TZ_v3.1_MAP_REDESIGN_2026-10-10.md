## 0. ГОЛОВНА КОМАНДА ВИКОНАВЦЮ

**Не створюй картинку або окремий demo замість робочої програми.** Проведи інвентаризацію чинного production-шляху; підготуй інтерактивні дизайни **всіх екранів**; реалізуй їх у **єдиному shared React UI**; під'єднай до справжніх станів API; перевір кожну дію у браузері, в PWA й у Capacitor iOS; випусти докази E2E. Жоден дизайнерський крок не повинен знищувати наявну коректну бізнес-логіку, дані та закріплені продуктові рішення. Спочатку закріпи source-of-truth Site/Server/iOS/umbrella з SHA і migration versions: гілки можуть містити РІЗНІ версії інтерфейсу. Додавай зміни еволюційно, не переписуй продукт із нуля. Заведи поелементну матрицю `контрол → обробник → маршрут → API → стан → повідомлення → тест` і здай її без пропусків.

**Пріоритети:** `P0` — обов'язково для заявленого запуску / безпека та цілісність; `P1` — обов'язково перед включенням відповідної функції для реальних людей; `P2` — масштабування, коли вже є відповідний партнер чи попит. Позначка P1/P2 не дозволяє показувати ще не реалізовану функцію як доступну. Кожну функцію маркувати `DONE / PARTIAL / NOT_IMPLEMENTED / BLOCKED_EXTERNAL`, підтверджувати тестами, не видавати оцінку за факт.

## 1. ПРОДУКТ: ЩО МИ ПРОЄКТУЄМО

**MARSHGO — «Один пошук. Уся дорога».** Український мультимодальний транспортний маркетплейс із попутками, приватними поїздками, ліцензованим комерційним транспортом, маршрутками/автобусами, міським електротранспортом, метро, залізницею, таксі, велосипедом, самокатом, каршерингом, трансферами та необхідними пішими сегментами. Людина не повинна знати постачальників заздалегідь: вона задає A→B, а MARSHGO порівнює реальні доступні варіанти за часом, повною вартістю, пересадками, пішою відстанню, актуальністю та надійністю. Якщо відповідних пропозицій немає — можна опублікувати запит із бюджетом. Водій може публікувати власну поїздку АБО лише навігувати та за окремою згодою підбирати пасажирів за маршрутом.

**Необговорювані правила:** не рекламувати неіснуючих інтеграцій; не використовувати чужі логотипи без прав; не підставляти деморейси та вигадані ціни до справжнього пошуку; не обіцяти фоновий GPS звичайній PWA; не підміняти підтверджене бронювання інформаційним розкладом; не викривати паспорт/документи, точний GPS, телефон без підстав; не змішувати Community-попутку з ліцензованим PRO-перевізником. Для **справжніх приватних Community-попуток — 0% комісії MARSHGO**, водій вказує власну суму за місце; юридичні умови щодо непрофесійного перевезення перевіряються окремо. Монетизація партнерських таксі/трансферів/квитків, B2B/SaaS і позначеного просування — лише на підставі договорів. Не ставити фіксовану ціну попутки від системи.

### 1.1 Ролі й однаковість інтерфейсу

`Гість`, `Пасажир`, `Водій Community`, `PRO/перевізник`, `Адмін`, `Модератор`, `Підтримка`, `Партнер` (останні — за підтвердженими доступами). Один обліковий запис для поїздок як пасажира й як водія. **Немає двох окремих домашніх сторінок, немає глобального обов'язкового перемикача «Я водій/пасажир»**: роль визначає конкретна дія. Якщо дія потребує авто/верифікації — коротке пояснення і deep link до необхідного кроку з поверненням до незбереженого наміру.

### 1.3 Глобальна навігація — остаточно

**Завжди рівно п'ять нижніх позицій на мобільному:** `Головна | Пошук | [великий круглий +] | Мої поїздки | Профіль`. Симетрично дві ліворуч і дві праворуч. `+` — центр **і дія**, а не шоста вкладка. Немає окремих нижніх `Маршрут`, `Чати`, `Заявки`, `Налаштування`.

**Верхній бар:** бренд/logo → за контекстом місто/заголовок → **окрема кнопка «Повідомлення» (іконка чату) → окрема кнопка «Сповіщення» (дзвіночок)**. Два окремих badge непрочитаного, незалежні маршрути й списки. Аватар може бути допоміжним входом у той самий Профіль за наявності місця, але не витісняє двох кнопок. Theme toggle **тільки** `Профіль → Налаштування → Вигляд`: `Системна` (default), `Світла`, `Темна`.

**Відповідність термінів:** `Пошук` = усі способи доїхати; `Поїздка водія` = опублікована пропозиція/рейс; `Заявка пасажира` = попит із бюджетом; `Мої поїздки` = заплановані/активні/завершені/скасовані, власні пропозиції та заявки; `Маршрут` = шлях A→B/Journey у контексті, не глобальна вкладка.

## 2. ВІЗУАЛЬНИЙ СТАНДАРТ — PREMIUM MARSHGO

### 2.1 Напрямок

Власний преміальний стиль MARSHGO; якість і простота жестів рівня Apple Maps, але **без копіювання чужої фірмової карти чи перемикачів «як Google/Waze/Apple»**. Враження «технологічно, впевнено, красиво»; не «геймерський HUD» і не перевантажений неоном. Основний інтерфейс — чисті світлі панелі, великий читабельний текст, виразна синя дія, реальні фото авто, зрозумілі дорожні лінії. Темна тема — справжня темна палітра й стиль MapLibre, не CSS-invert цілого полотна. Фантастичність зосереджена в **живій навігаційній карті**: делікатне холодне підсвічування активного маршруту, глибина 2.5D, акуратні транспортні спрайти, чіткі акценти. Той самий layout у light/dark; тема не змінює бізнес-семантику.

### 2.2 Дизайн-токени (початковий базис, перевірити контраст)

`brand-blue #1769ED / #1769F4` (затвердити один у token ADR), `navy #081B35`, `ink #10223E`, `surface-light #FFFFFF`, `page-light #F5F8FD`, `muted #62718A`, `border #DFE7F1`, `success #16845C`, `warning #AE6C00`, `danger #BE3440`; dark `page #070E1B`, `surface #0B1730`, `ink #F4F8FF`, `border #24334C`. Дизайн-token ADR визначає кінцеві контрастні значення, семантичні кольори 12 категорій та кольори маршрутних ліній без залежності змісту від самого кольору. 4/8 px spacing system, радіуси 12/16/24, мінімальні touch targets 44×44 CSS px (у навігації 48–56), текст полів 16px для iOS без autozoom, системний/Inter із нормальною кирилицею, контраст WCAG 2.2 AA, focus rings 2+ px, reduced motion.

### 2.3 Фірмові компоненти

`AppShell`, `TopBar`, `BottomDock`, `PrimaryCTA`, `SecondaryButton`, `SearchPlaceField`, `PlaceAutocomplete`, `MapPointPicker`, `SwapPlaces`, `DateTimePassengers`, `TransportChip`, `TransportMultiSelect`, `ProviderSelect`, `StrategySelect`, `JourneyCard`, `LegTimeline`, `DriverCard`, `VehicleGallery`, `PriceBreakdown`, `AvailabilityBadge`, `FreshnessLabel`, `BookingConfirmSheet`, `TripStatusTimeline`, `NegotiationOfferCard`, `ChatComposer`, `NotificationCard`, `MapLayerSheet`, `VehicleLiveCard`, `StopLiveCard`, `RendezvousSheet`, `RescueSheet`, `PhotoVerification`, `ErrorPanel`, `EmptyState`, `OfflineBanner`, `PermissionPrompt`, `Skeleton`. Кожен — **справжній доступний компонент**, не вставлена картинка із намальованими кнопками.

### 2.4 Mobile / tablet / desktop

- `320–599px`: один основний canvas, нижній dock із 5 позицій, форми по вертикалі, прокручувана стрічка чіпів із явною кнопкою «Усі види/Ще», sheets; не обтинати «Мої поїздки», не перекривати кнопку чату/дзвіночка; safe-area Apple.
- `600–767px`: адаптувати композицію landscape/малий планшет; поля й CTA не перекривати клавіатурою.
- `768–1199px`: список/деталі разом із картою в split-view, зручні панелі, коректний touch/keyboard.
- `≥1200px`: ліва панель пошуку/результатів приблизно 400–480px + велика справа карта; ті самі п'ять destination у компактному dock/навгації та ті самі дві верхні дії, без семантичного розширення до семи вкладок.
- `svh/dvh`, `env(safe-area-inset-*)`, keyboard viewport, 200% zoom, RTL-safe layout architecture, no page-wide x-scroll; device model не визначає бізнес-логіку.

### 2.5 Знімки/візуальні артефакти дизайну

Для **кожної** сторінки: mobile light, mobile dark, desktop light, desktop dark + loading/empty/error/permission/offline (де мають сенс); компоненти порівнювати side-by-side. Для карти окремо: 2D, 3D, гібрид, транспортний пресет, нічний вигляд, Live Pickup, активна навігація. Кожен макет зв'язаний з route/control ID та кінцевим React-компонентом. Жодного неоново-синього «показового» мокапу без реальної можливості швидкого GPU-рендеру.

## 3. КАРТА ВСЬОГО ВЕБІНТЕРФЕЙСУ / ROUTING CONTRACT

Нижче — **цільові назви URL**. Потрібно звірити з існуючим router; підтримати поточні deep links і 301/redirect/alias, де дозволено; не зламати старі посилання із сповіщень. Шлях API не можна припускати лише з URL UI.

| Сімейство | Route | Екран і підекрани |
|---|---|---|
| Публічний | `/` | Головна, швидкий початок; маркетингові блоки відділити від основного UX |
| Вхід | `/auth`, `/auth/otp`, `/auth/onboarding` | телефон, OTP, пояснення доступів, повернення до наміру |
| Пошук | `/journeys/search` | форма, результати, карта, filters/providers, strategies, recent/favorite searches |
| Пошук | `/journeys/search?from=…&to=…` | shareable/restorable state, тільки несекретні параметри |
| Деталі Journey | `/journeys/:id` | legs, timeline, reliability, карта, ціна/варіанти |
| Деталі пропозиції | `/offers/:id` | водій/авто/умови/місця/підтвердження |
| Бронювання | `/bookings/:id` | квиток/резерв/зміна/скасування/чат/посадка |
| Дії `+` | `/demands/new`, `/offers/new`, `/navigate`, `/demands` | заявка, пропозиція водія, навігація, заявки для водія |
| Заявки | `/demands/mine`, `/demands/:id` | заявка, пропозиції, історія торгу, редагувати/скасувати |
| Мої поїздки | `/trips` | `Зараз/Заплановані/Історія`, види власних активностей, архів/скасовані |
| Конкретна поїздка | `/trips/:id` | статус, карта, учасники, навігація, Live Pickup, спільне завершення |
| Навігація | `/navigate` | start/preview/active/paused/offline/completed; не нижня вкладка |
| Повна карта | `/map` | map canvas, transport preset/layers, stop/vehicle cards |
| Повідомлення | `/messages`, `/messages/:id` | розмови, переговори, чат і контекст поїздки |
| Сповіщення | `/notifications` | системний inbox, фільтри, read-all, deep links |
| Профіль | `/profile`, `/profile/edit` | аватар, ім'я, рейтинг, телефон/доступи, мої дані |
| Авто | `/profile/vehicles`, `/profile/vehicles/new`, `/profile/vehicles/:id` | фото, рік/номер/місця/умови, редагування/активація |
| Верифікація | `/profile/verification` | рівні довіри, завантаження/перевірка документів |
| Налаштування | `/profile/settings`, `/profile/settings/appearance`, `/profile/settings/notifications` | тема/мова/сповіщення/навігація/доступність |
| Безпека | `/profile/privacy`, `/profile/security`, `/profile/blocked`, `/profile/data` | сесії, блокування, експорт/видалення, згоди |
| Платежі | `/profile/payments` | історія/методи **лише якщо є реальний інтегрований PSP**; інакше неактивний чесний стан |
| Підтримка | `/help`, `/safety`, `/reports/new`, `/reports/:id` | FAQ, скарга, екстрена інструкція, звернення |
| Партнерський кабінет | `/partner/*` | свій парк/рейси/розклад/місця/підтримка (по договору) |
| Адмінка | `/admin/*` | окремий захищений app shell, без публічного bottom dock |
| Системні | `/offline`, `/403`, `/404`, `/500` | коректні пояснення, повернення, retry |

**Навігаційний інваріант:** URL→екран→selected entity→активна нижня вкладка повинні бути детермінованими. `/messages/:id` висвітлює Повідомлення вгорі, не створює 6-ї нижньої вкладки; `/bookings/:id` і `/trips/:id` контекстно належать «Моїм поїздкам». Browser back/refresh/deep link відновлюють стан без застарілого `selectedJourney` із іншої поїздки.

## 4. ГЛОБАЛЬНИЙ APP SHELL І КОНТРАКТИ КНОПОК

**Header:** натискання лого → Home; назва міста → дозволений вибір міста/геолокації; Message bubble → `/messages`; Bell → `/notifications`; badge кожної системи має свій серверний лічильник; avatar, якщо є → `/profile`. На 320px дві верхні кнопки завжди доступні, не сховані в hamburger. У header НЕ показувати перемикач теми, demo production-switch, двозначні «Пошук/Усі рейси» як дубль вкладок. Demo-режим технічно ізольований і недоступний у реальному release build, без прихованих фейкових даних.

**Bottom nav:** рівно 5 інтерактивних областей. На всіх робочих екранах, окрім явно повноекранної навігації, авторизації та fullscreen camera, показувати dock із safe-area. Кожна кнопка має доступну назву, focus, selected state, відповідає точному URL. `+` відкриває action sheet, не виводить користувача з поточного контексту, закриття повертає focus до плюсика. Якщо натиснути вже активну вкладку — прокрутка до верхньої частини або повернення з вкладеного підекрана, але не створення другої форми й не reset підтвердженої поїздки.

**Глобальні сервіси:** Toast/InlineError (помилка біля поля, не тільки toast, який зник), Skeleton, empty-state із конкретною наступною дією, глобальна обробка 401 із поверненням до наміру, OfflineBanner, GPS-permission helper, індикатор «Дані оновлено ...», зовнішній перехід із підтвердженням, системний share-link, контроль back/forward/deep links, локальні чернетки форм без зберігання OTP чи чужих GPS-даних. В усіх модальних вікнах focus trap і restoration, gesture/back close без втрати даних, застереження при незбережених змінах.

**Вимога інвентаризації:** після аудиту створити для **кожної** кнопки/піктограми, field action, gesture, clickable card, tab, sheet, selected map feature ID запис: екран/URL, мітка/aria, видимість за роллю, умова доступності, onClick, destination, API method, success server state, invalid/conflict state, loading/offline/failure, analytics event, test ID. Декоративних інертних кнопок бути не повинно.

## 5. «ГОЛОВНА» — ПРОДУКТОВИЙ СТАРТ, НЕ ДУБЛЬ «ПОШУКУ»

**Ціль:** за 1–2 дії відкрити потрібний сценарій. Основна композиція: компактний бренд-хедер; велике «Куди їдемо?»; преміальна легка ілюстрація/анімація транспортного маршруту чи взаємодії водій↔пасажир (без важкої живої карти); три великі дії; короткий A→B quick-search без розгорнутого набору провайдерів; горизонтальні 12 транспортних чіпів (видно 4–5 і явне «Усі види»); **«Знайти маршрут» СТРОГО ПІСЛЯ чіпів**; активна поїздка/коротка картка за наявності; контекстні останні маршрути лише коли корисні. Не робити зайву довгу головну, що змушує скролити до основних дій.

### 5.1 Три основні дії

| Назва | Призначення та перехід | Особливості |
|---|---|---|
| `Почати навігацію` | `/navigate`, початковий screen із «Куди їдемо?» або GPS | Можна відкрити навігацію/карту до введення destination; власну поїздку не потрібно публікувати. Попутники — лише окремо за згодою верифікованого водія. |
| `Шукати поїздку` | `/journeys/search` | Основний мультимодальний пошук; не публікувати заявку автоматично. |
| `Запланувати поїздку` | якщо контекст не визначений — вибір «Пропоную поїздку / Шукаю місце»; інакше відповідна форма | Водій → `/offers/new`; пасажир, що хоче опублікувати попит, → `/demands/new`. Ніколи не скидати форму без згоди. |

### 5.2 Quick search

Поля `Звідки`, `Куди` (автозаповнення, точка на карті, поточний GPS, swap), компактні дата/час/кількість людей за потреби, чіпи `Усі` + точні 12 категорій у погодженому порядку. Клік конкретних типів підтримує мультивибір. `Знайти маршрут` переводить до повного Search з передачею A/B, часу, пасажирів і обраних категорій; якщо поля вже валідні, може одразу запустити ту саму **єдину** пошукову операцію. Провайдери та складні опції — у повному Search. Без місця призначення — focus на поле, не фіктивний запит.

**Контекстна поїздка:** якщо активна — компактна, без другого dashboard: `Відкрити поїздку` → `/trips/:id`, `Навігація` → її активна GPS-сесія, `Повідомлення` → відповідна розмова. Вміст Home не повинен перетворитися на каталог усіх поїздок, для цього є Search/Trips.

## 6. «ПОШУК» — ЄДИНА МУЛЬТИМОДАЛЬНА ФОРМА

### 6.1 Порядок і структура (обов'язковий)

1. Header із незалежними Messages і Notifications.
2. Заголовок «Знайди маршрут / Усі способи дістатися в одному пошуку».
3. `Звідки` і `Куди` з swap, GPS та вибором точки на карті.
4. `Коли`: зараз / виїхати о / прибути до; дата, конкретний час, часовий інтервал за потреби.
5. `Пасажири`: 1…з дозволеним верхнім обмеженням, сервер перевіряє місткість конкретного рейсу.
6. `Види транспорту`: горизонтальна стрічка з 12 canonical categories, мультивибір, `Усі`, `Усі види`/повна сітка.
7. `Провайдери`: тільки постачальники, що мають обраний тип і підтримуваний capability у цьому місті; `Усі провайдери` / вибрані.
8. `Стратегія`: три UI-варіанти **Оптимальний / Найшвидший / Найдешевший**; інші backend scoring modes не утворюють нову четверту/п'яту головну кнопку без погодження.
9. Додаткові `Фільтри`, інтегровані поряд із потрібним блоком або в sheet: максимальна ціна, пересадки, максимальна довжина ходьби, багаж, кондиціонер, дитяче крісло, тварини, доступність, верифікація, час очікування — тільки коли відповідають типу.
10. Велика єдина CTA **`Знайти маршрут` ПІСЛЯ всіх виборів**, не перед транспортом.
11. Після submit — `Список / Карта` або adaptative split; не приховувати виправлення фільтрів.

### 6.2 Поля та помилки

- Place picker: autocomplete + історія без секретних адрес у глобальному analytics; GPS точність/permission, map pin picker (зберігати **ім'я + lat/lon + placeId/provider**). Якщо GPS відхилений — ручне введення. Swap повністю міняє іменовані місця з координатами, не тільки тексти. Недозволено трактувати текст «Львів» без координат як точно геокодовану точку.
- Time: timezone Europe/Kyiv для введення, абсолютні серверні timestamps UTC/ISO з offset, DST invalid/ambiguous time, обмеження минулого. `Прибути до` — окрема семантика планування, не підміняти виїздом у цей час. `Зараз` реальний поточний час, оновлювати при новому submit.
- `Усі`: дефолтні доступні/підтримувані типи; клік окремої категорії вимикає `Усі` і додає до Set; клік обраної видаляє; якщо Set порожній — повертається `Усі` (не «нічого не знайдено»). Міські disabled категорії або видимі з поясненням «Поки не підключено», або приховані за узгодженою registry policy; **не дозволено** показувати їх як live provider або придатні до booking.
- Provider chips: з'являються тільки після відповідного type; зміна type скидає невалідні provider IDs, не губить валідні; показує `Доступний / Лише розклад / Немає зв'язку / Очікує договору`, доступність із серверного registry.
- `Пішки` не показується як кнопка. За потреби у «Фільтрах» є `Менше ходьби` або max walking distance, але автоматичні короткі переходи можуть бути необхідними, про це повідомити; не генерувати нереальний пересадочний зв'язок при забороненій ходьбі.
- Успішний маршрут навіть без перевізника: за доступної маршрутної геометрії можна показати **орієнтир A→B як базовий дорожній/пішохідний шлях** із позначкою `План шляху — не знайдений рейс`; не вигадувати громадський транспорт або ціну. Якщо маршрутизатор недоступний, пояснити причину та дозволити повторити.

### 6.3 Поетапний UX

`IDLE → VALIDATING → GEOCODING → SEARCHING → PARTIAL_RESULTS|RESULTS|EMPTY|ERROR`; stale requests cancel, `Знайти маршрут` disable/loader під час submit; timeouts одного провайдера → часткові результати з чесним списоком недоступних джерел. Search criteria й view-mode живуть у URL/query cache та переживають перехід між вкладками, refresh/back/forward; персональні координати не виставляти публічним індексованим deep link без згоди. Не запускати два незалежні механізми `SearchExperienceV6` і старий marketplace offers search за однією CTA.

## 7. РЕЗУЛЬТАТИ / JOURNEY DETAIL / ЦІНА / БРОНЮВАННЯ

### 7.1 Список і карта одного результату

Для кожного Journey: route label, origin/destination, загальний час, час відправлення і прибуття, пішки, очікування, пересадки, конкретні транспортні legs, назва провайдера, freshness/last checked, seat availability, тариф **за місце/авто/квиток/добу** і **повна підсумкова сума для обраної кількості пасажирів**, fee/комісія за правилами. Якщо частина вартості невідома, показувати `Від ... / Орієнтовно / Немає підтвердженої ціни`, а не фальшивий total. Дорога й час очікування для пересадок реально перевірені через transit planner. Позначки «Оптимальний», «Швидший», «Дешевший» — лише якщо підраховані на фактичному наборі результатів, без дублюючої реклами.

На мобільному — акуратні картки; на desktop — список ліворуч, карта праворуч. `Натиснути картку` → виділити маршрут на карті, `Показати на карті` → zoom fit цього Journey, `Детальніше` → `/journeys/:id`, `Назад` → ті самі результати без повторного введення.

### 7.2 Деталі сегментів

**Попутка:** фото реальної машини, фото водія, репутація із даними, модель/рік/номер у дозволеній видимості, час, точка посадки/висадки, 1/2/3+ місць, вільні місця, багаж, кондиціонер, дитячі умови, тварини, правила, ціна за місце й повний total, `Забронювати`, `Зв'язатися` коли дозволено, `Поскаржитися`.

**Міський транспорт:** маршрут №, напрям, carrier, лінія, зупинки, розклад, наступний транспорт/ETA лише якщо підтверджено даними, `Показати на карті`, `Стежити`/нагадування, джерело часу, реальна актуальність, позначка `Розклад` vs `Live`.

**Поїзд/міжміський автобус:** перевізник, час/вокзал/платформа за наявності, клас, багаж, пересадки, квиток, конкретна ціна або `від`, `Купити` лише при партнерському API/URL. На зовнішньому redirect показати, що оплата й умови — на стороні постачальника.

**Таксі/трансфер:** оператор, категорія авто, кількість пасажирів, estimated vs confirmed quote, pickup, luggage, `Замовити` тільки при інтеграції, інакше `Перейти до партнера` чи `Запитати вартість`.

**Велосипед/самокат/каршеринг:** дійсна станція/об'єкт і freshness, зони прокату/повернення (pickup+drop-off), батарея коли є, тарифи/депозит/правила, легальний спосіб бронювання/запуску. Не робити придумані доступні самокати на карті. Для прокату іноді важливі геозони та age/ID requirements; показувати тільки з provider data.

### 7.3 Перевірка бронювання

Три **чітко розмежовані** capabilities: `INFO_ONLY` (інформація/розклад, без місця), `EXTERNAL_BOOKING` (посилання до партнера), `IN_APP_BOOKABLE` (сервер підтверджує hold/book). Кнопка залежить від capability, не від кольору картки. Journey із кількома legs не стає повністю «підтвердженим», якщо заброньований лише один leg. Після `Забронювати`: серверна перевірка inventory, ціни й ревізії, форма `Перевірити деталі` із загальною сумою, посадкою/правилами, явне `Підтвердити`; idempotent POST; відповідь підтвердження або pending/rejected; `Мої поїздки` після успіху. Втрата відповіді → відновити по idempotency key, не повторно бронювати. Деякі партнери підтримують тільки info/redirect — не малювати їм власний «квиток» без контракту.

### 7.4 Порожні результати

Показати: чому не знайшли, `Змінити час`, `Додати типи`, `Змінити фільтри`, `Опублікувати заявку` (перенести A/B, date, passengers, бажаний budget), `Стежити за маршрутом` за opt-in. Не вигадувати «50 маршрутів поблизу» як live для порожнього результату. Повний базовий геометричний шлях і можливі піші/дорожні варіанти — за реального маршрутизатора; чітко пояснювати, що це не рейс або доступна машина.

## 8. MARSHGO MAP V2 — ГОЛОВНИЙ РЕДИЗАЙН

**Візуальні референси від власника (10.10.2026):** оригінали в пакеті `reference_images/` (A/B/C); ескіз 1 — презентація трьох навігаційних режимів із денним/нічним виглядом; ескіз 2 — пошукова карта з легким ізометричним містом і фільтрами; ескіз 3 — мінімалістична схема доріг із неоновим маршрутом. Усі три є дизайнерським напрямком, а не буквальним знімком допустимих кнопок, географії, рейсів або підтвердженого GPS. Див. обов’язковий розділ 8.7–8.14.


### 8.1 Головна дизайнерська ідея

**Не зробити гру GTA в браузері.** Зробити розкішну, впізнавану, неймовірно зручну навігаційну карту на вже наявному **MapLibre GL JS**, яка плавно працює і на середньому iPhone. Власна стилізація: точна дорожня геометрія, спокійний базовий рельєф, легка глибина в 3D, контрастний маршрут із м'яким світловим halo (2 легкі WebGL line layers, не postprocessing), розумний рівень деталізації за zoom, великі читабельні назви, зрозумілі точки посадки/пересадок. Ніяких важких 3D-будівель усіх районів чи тисяч DOM маркерів; GPU-рендеринг і sprite atlas. Пам'ятати що це транспортний продукт: щоразу користувач повинен бачити *де я, куди їду, хто/що їде, де сісти, коли приїде, що робити далі*.

### 8.2 ТРИ режими навігаційної карти × ДЕНЬ/НІЧ — шість візуальних комбінацій

**Остаточно:** в активній навігації користувач має рівно **три режими**: **Простий (2D)**, **3D**, **Супутник (гібрид)**. Кожен має денну й нічну презентацію — **6 комбінацій**. Це не шість різних рушіїв і не шість масивних scene graph; спільний MapLibre, мінімум доступних styles + контрольовані layers/camera. **Транспорт — окремий шар або швидкий preset над Простим режимом, не четверта кнопка режимів навігації.** Визначення 12 видів транспорту не пов’язане з кількістю режимів карти.

| Режим навігації | День | Ніч | Реалізація |
|---|---|---|---|
| **Простий 2D** | світла, лаконічна карта доріг, зелені парки, виразні підписи | глибокий синьо-графітовий фон, світлі назви й дороги, делікатне підсвічування | vector basemap із двома стилями, pitch≈0 |
| **3D** | легка перспектива, вибіркові спрощені квартали й орієнтири | та сама геометрія, затемнені об'єми, м'яке світло ключових вулиць | той самий vector source, pitch 40–55° за пристроєм, екструзія лише там, де дані/бюджет дозволяють |
| **Супутник / гібрид** | легальна супутникова/аерофотопідкладка + чіткі лінії та підписи | супутникова підкладка з контрольованим затемненням/контрастом + читабельні підписи і маршрут | ліцензійні raster tiles + vector overlays; **не генерувати фальшиві нічні супутникові світлини** |

Контроль режиму:  `Режими карти` → radio segmented sheet `Простий / 3D / Супутник` із поточним selected state; окремий `Шари` → `Громадський транспорт / Зупинки / Попутки / Прокат / Каршеринг` та інші доступні шари. Швидка дія `Показати транспорт` вмикає transit overlay або preset 2D, але **не** додає четвертий режим до трійки навігації.

День/ніч: системна тема — дефолт; ручний вибір `Системна/Світла/Темна` лише у `Профіль → Налаштування → Вигляд`. У навігації допускається окремий швидкий перемикач **вигляду карти** `Авто/День/Ніч` всередині листа «Режими карти», який не змінює глобальну тему застосунку; якщо не реалізовано окреме навігаційне перевизначення, достатньо автоматичного перемикання за темою. Перемикач у верхньому глобальному header заборонений. Не прив'язувати ніч автоматично лише до години 19:00: поважати system theme та призначене mapAppearance і дозволяти зрозуміле перевизначення. Зберігати останній режим карти; при запуску активної навігації за потреби запропонувати 3D, але не насильно скидати вибір користувача. Не змінювати `selectedJourney`, фільтри чи бронювання при зміні режиму.

### 8.3 Легкі рухомі транспортні іконки замість стрілок

Показувати **маленькі правдоподібні 2D/2.5D силуети**: маршрутка/міський автобус/тролейбус/трамвай/таксі/легковик/поїзд, транспортна піктограма не більше 1–2 GPU symbol layers + невеликий маршрутний номер. За bearing піктограма повертається (крім тексту route badge). Активний для користувача транспорт підсвічується; пасивні спрайти невеликі, не перекривають вулиці. Жодних 3D mesh на кожне авто. Свідомо не замінювати фізичні GPS-координати «стрілками руху» по статичному розкладу.

**Live vehicle motion pipeline:** підтверджений дозволений provider feed (GTFS-RT VehiclePositions/офіційний GPS/договірне API) → отримання `lat/lon/bearing/observedAt/receivedAt/vehicleId/tripId/routeId/providerId/accuracy/ttl` → коректне spatial+trip matching до road/line shape → GPU snapshot + websocket deltas або timed polling fallback → плавне обмежене до реальних timestamp інтерполювання → значення stale при timeout → зупинити екстраполяцію, потьмяніти та прибрати за TTL. Не показувати `LIVE` або «прибуде за 2 хв» без підтвердженого realtime / validated prediction engine. Якщо є лише GTFS static — показувати `За розкладом` та часові вікна, **не маленьку рухому GPS-маршрутку як факт**.

**Маркер:** тип піктограми + номер + напрям за можливості; tap відкриває vehicle bottom sheet із: `№`, `напрям`, назва оператора, last update, точність/статус, наступні зупинки (тільки за даними), час прибуття, `Показати весь маршрут`, `Стежити`, `Закрити`; long press — пояснення чи контекст. Hover лише допоміжний, доступний список поза MapLibre canvas для VoiceOver.

### 8.4 Зупинки, маршрути, комбінований шлях

Tap stop → `назва / вид транспорту / маршрути / наступні прибуття / джерело / дата оновлення / Переглянути лінію / Побудувати сюди`. Tap route/polyline → виділити відповідну лінію, помірний zoom, показати всі зупинки/послідовність і панель розкладу. Tap rental → дійсні station availability, батарея, зона повернення, provider link. Кожний сегмент Journey має свій атрибут `mode`, geometry, provider, duration, start/end; `Пішки` пунктир/текст, транзит суцільна лінія відповідної семантики, Community/taxi/mobility інші patterns. Не кодувати інформацію тільки кольором. У результатах обрана картка синхронізує виділений маршрут і розгорнуту маршрутну timeline, а карта не змінює вибір без події користувача.

**Стикування A→B:** початок, пішки до зупинки, час очікування, громадський транспорт/попутка, пересадка, остання миля, ETA, вартість. Коли немає постачальника — показати базову геометрію від route provider та чесний state `Поки немає доступних рейсів`; не залишати чорну/порожню карту при валідній геометрії. Розрахунок walking transfer повинен використовувати реальну пішохідну мережу, не пряму по координатах; міряти buffer і ризик не встигнути.

### 8.5 Карта в навігації, безпека під час руху

Active navigation: heading-up 3D за обраним режимом, точна GPS-позиція й accuracy circle, наступний маневр, назва вулиці, відстань до маневру, швидкість/обмеження **лише коли доступні достовірні дані**, час до кінця/ETA, remaining distance, `Звук`, `Огляд`, `Компас`, `Моє місце`, `Зупинити`. Великий шрифт/натискання, мінімум дій і без переписки за кермом; stop-to-interact для торгу/бронювання, лаконічні read-only підказки. Turn-by-turn тільки з routing `steps` та route matching, не генерувати інструкції лише з координатної polyline. При виході з маршруту `перевизначення → нова геометрія → показати зміну ETA`; попереднє бронювання й stop order не губляться.

**Навігацію може почати будь-який авторизований користувач за GPS-згодою**. Режим пошуку пасажирів доступний лише для належно допущеного водія з верифікованим авто, і лише після окремої дії `Підбирати попутників дорогою` з налаштуванням місць/детуру та поясненням location sharing. Якщо цей режим вимкнений — це звичайний навігатор, без трансляції пасажирам.

### 8.6 Performance/Licensing/Errors

MapLibre+PMTiles/vector tiles (ліцензійні або self-host), raster для satellite/hybrid за контрактом; **не bulk offline з public tile.openstreetmap.org**; належна OSM attribution видима. Graph geometry/route provider OSRM-compatible, adapter можливо інший. HERE/TomTom traffic — передбачені **вимкнені** adapter flags до реальних договорів/цін; не зображати фіктивні пробки. GPU symbols та GeoJSON sources, кластеризація або type-bbox aggregation; оптимальна межа LOD zoom 10–13; viewport subscriptions; batching position changes, throttling pan, suspended updates hidden, memory cleanup після unmount. Reduced motion, не анімувати під час заморозки GPS.

**Failure cases:** WebGL unavailable → route list + steps/статична схема із чесним попередженням; tile failed → fallback basemap або видимий degraded canvas, але itinerary залишається; GPS denied → ручний origin; location stale → timestamp, призупинення live matching; GTFS-RT down → schedule-only; WSS disconnect → snapshot/poll and reconnect; offline → licensed saved pack and instructions where installed; немає pack → `Цей маршрут недоступний офлайн`; provider unavailable не перетворює інші маршрути на помилку 500.

### 8.7 ТРИ НАДАНІ ЕСКІЗИ: що брати, а що заборонено копіювати (P0)

**Ескіз A — «Навігація в 3 режимах» (шість телефонів):** головний visual authority для різниці Простий/3D/Супутник, день/ніч, поведінки під час активної навігації. Взяти: ясний маршрут, наступний маневр, точку GPS, транспорт на маршруті, велику картку часу прибуття, акуратний 3D та light/dark. Не переносити ілюстративні `36 км/год`, обмеження `50`, `12 хв` у робочу програму як константи; тільки real route/sensor/legal verified road data. Нижній dock зберегти рівно canonical 5.

**Ескіз B — «Пошук на карті в денному/нічному вигляді» (два телефони):** visual authority для **ПОШУКУ**, а не для повноекранної навігації. Взяти: A/B-поля зверху, компактну горизонтальну стрічку категорій, карту на нижньому полотні, контрастний обраний маршрут, невеликі icons транспорту, виклик шарів, розумний bottom sheet результату, світло/темну карту. Не копіювати помилкову нижню панель **Головна / Пошук / Маршрут / Повідомлення / Профіль**: вона СКАСОВАНА. Не показувати speedometer, turn instruction і speed limit у звичайному пошуку. На ескізі видно лише 5 типів плюс `Усі` через горизонтальний скрол — у реалізації мають бути всі **12**, без дублюючих окремих категорій та з можливістю явного повного вибору.

**Ескіз C — «Карта, що рухає місто» (два телефони):** visual authority для **легкого векторного базового стилю**. Взяти: мінімум вуличного шуму, просту геометрію кварталів, м'який неоновий cyan/blue маршрут, читабельний тон темної карти, крапкове атмосферне світло на головних магістралях, ясні GPS-кнопки, низьку щільність декоративних символів. Не копіювати його нижню панель **Карта / Маршрути / Транспорт / Обране / Профіль**, hamburger як заміну canonical navigation, окреме четверте глобальне меню «Транспорт» і перемикач теми над картою. Жодні світлові точки не мають бути реальними окремо відрендереними 3D-ліхтарями.

**Правило пріоритету:** `docs/PRODUCT_CANON.md` і погоджена логіка сторінок > вимоги цього Master TZ > композиція/естетика на ескізі > текст/кнопки/числа випадково намальовані на ескізі. Жоден екран з ескізів не є затвердженням старої нижньої панелі. Кожен дизайнерський кадр має бути перемальований із правильними п'ятьма позиціями та двома верхніми кнопками.

### 8.8 Строге розмежування ПОШУКУ та НАВІГАЦІЇ (P0)

| Властивість | `Пошук` | `Навігація` |
|---|---|---|
| Основне запитання | «Як дістатися A→B?» | «Куди рухатися зараз?» |
| Поля | Звідки, куди, час, 12 категорій, провайдери, стратегія | Destination, поточний GPS, маршрут, voice/controls |
| Карта | огляд результатів і порівняння Journey | following GPS + маневри та стан руху |
| Нижня частина | draggable bottom sheet із Journey/result cards | компактна ETA/distance панель + driving-safe controls |
| Лічильник швидкості | **Немає** | є тільки за реальним датчиком/дозволом |
| Обмеження швидкості | **Немає** | лише із достовірного дорожнього data source, інакше приховати |
| Зміна транспорту | повні 12 multiselect; провайдери | не змінювати бізнес-пошук під час кермування; лише контекстний перегляд шарів |
| GPS | опціонально для A і «поруч зі мною» | активний foreground permission і точність; навігаційна сесія |
| Автопідбір попутників | **не стартує** після звичайного пошуку | тільки для верифікованого водія за явною згодою |

Взаємозв'язок: `Пошук → обраний Journey → Деталі → (бронювання за capability) / Показати маршрут → Навігація`, з передачею реальної геометрії, точки посадки/висадки, stop order, journey/booking ID; `Навігація → активна поїздка → Мої поїздки`, але звичайна персональна навігація без бронювання не повинна штучно створювати booking. `Пошук` зберігає фільтри/URL; перехід у навігацію не робить дубль booking чи нову заявку. При back на Search потрібно відновити результати/позицію списку.

### 8.9 Мобільна композиція «Пошук із картою», за ескізом B (P0)

1. **Верхній глобальний bar:** MARSHGO; дві видимі незалежні іконки `Повідомлення` і `Сповіщення` з badge; вибір міста другорядний, за браку місця може бути всередині пошуку, але ці дві іконки НЕ зникають у hamburger.
2. **Форма A/B:** висота визначається контентом (не займати половину екрана), `Звідки? / Куди?`, GPS і swap, карта як place picker; датa/час/пасажири в компактному рядку/розкривному sheet.
3. **12 категорій:** чіп `Усі` + дванадцять затверджених, горизонтальний скрол зі зрозумілим сигналом продовження і відкриттям повної сітки; мультивибір, стан чітко помітний без кольору. Не відображати одні й ті ж категорії двома незалежними наборами checkbox.
4. **Провайдери і три стратегії:** компактно відображати в expandable filter sheet; CTA `Знайти маршрут` лише **після** виборів, доступна без нескінченного скролу в sticky action zone, що не перекриває bottom dock та keyboard.
5. **Результати:** мапа 35–65% видимої висоти залежно від пристрою, знизу drag sheet із ETA/ціною/сегментами. Sheet має collapsed/medium/expanded позиції; будь-який маршрут на карті та в списку синхронний. Поза результатами не малювати вигадану обрану лінію між A/B, якщо не виконано real routing.
6. **Керування картою:** два компактні видимі контролі праворуч `Моє місце` та `Шари`, за потреби `Огляд`; інтерактивні області 44–48px, не конфліктують із жестами scroll sheet.
7. **Нижня панель завжди:** Головна | Пошук | **+** | Мої поїздки | Профіль; safe-area, не накривати sheet чи CTA. На `Пошук` позначати активність саме Пошуку, не Маршруту.

### 8.10 Мобільна композиція «Активна навігація», за ескізом A (P0)

1. Верх: контекст поточної поїздки/дороги + велика картка **наступного маневру** (стрілка, реальна відстань, назва вулиці) і доступ до голосових підказок; глобальні Messages/Notifications або безпечний вихід до них зберігають доступність поза режимом кермування, але не спонукають до переписки.
2. Центр: **обраний режим** `Простий / 3D / Супутник` та стан `День/Ніч`, один активний GPS puck, орієнтація за bearing, маршрут найбільш виразний; альтернативні вулиці приглушені.
3. Праворуч: компактні `Recenter`, `Layers/Mode`, `Compass/Overview` без дубльованих float-controls. `Mute` або у верхній картці, або у правому стовпчику, але не двічі.
4. У нижній третині: компактна ETA картка `хв до прибуття`, `км залишилось`, `орієнтовний час прибуття`, `Завершити`; speedometer лише за даними датчика, speed limit лише з перевіреного джерела. За помилки GPS акуратно показати «Слабкий GPS» та accuracy, не перестрибувати маркер довільно.
5. Нижні 5 позицій зберігати **коли це безпечно і є місце**; якщо fullscreen driving navigation приховує dock, показати однозначну кнопку «Назад до Моїх поїздок»/«Вийти з навігації», після виходу canonical dock відновлюється. Ніколи не замінювати dock на інший набір п'яти кнопок як на ескізах B/C.
6. Перемикання денного/нічного вигляду, 2D↔3D↔Satellite НЕ перезапускає GPS-сесію, не втрачає маршрут, інструкцію, ETA або голос, не скидає увімкнене явним чином matching.

### 8.12 «Космічний» вигляд без важкого рендеру (P0)

**Нічні ліхтарі на магістралях, як відчуття Petal Maps:** не створювати тисячі фізичних об'єктів, point lights, real-time shadows, bloom postprocessing, particle systems або Three.js над MapLibre. Передбачити **один** стислий повторюваний патерн світлових рисок/точок для пріоритетних доріг у style layer/atlas (або взагалі пропустити декоративне світло на слабших GPU). Це естетичний ефект, а не дані про реальні працюючі ліхтарі. Зменшувати густину «вогників» залежно від zoom і performance tier; екрани з активною навігацією важливіші за декор.

**Світіння будинків:** не шейдерна симуляція освітлення кожного вікна. Лише легка відмінність стилю контурів або кілька статичних текстур/landmark symbols на вибраних central zoom; автоматично вимкнути у low-power/reduced-motion.

**Неонова лінія:** 2 map style layers — тонкий контур/halo і core; уникати CSS blur на canvas та багатьох накладених route line layers. Рекомендований core товщий за halo-візуальну засвітку, щоб шлях залишався чітким. На satellite halo з outline повинен залишати видимою підкладку.

**Іконки машин та маршруток:** статичний atlas із мінімальною кількістю піктограм; повертати за реальним bearing, batching updates; не моделювати кузов у 3D. Локалізація route number окремо від розвороту іконки. Не показувати іконки живого транспорту без дозволеного feed і freshness.

**Кластеризація/LOD:** окремі zoom thresholds; не показувати всю країну 1000-ма деталізованими об'єктами. Зменшити анімації на viewport зі слабкою GPU, hidden tab, швидкому скролі й навігації в тлі. Тестувати frame time, CPU, GPU memory, батарею, а не тільки Lighthouse Home page.

**Візуальна ідентичність:** власний MARSHGO navy+blue/cyan; світлий преміальний UI; нічний «космос» без кічу; дороги/зупинки/маршрути повинні бути зрозумілі для щоденних поїздок, а не тільки презентації.

### 8.13 Конкретний технічний MapLibre contract (P0/P1)

- Один `MapLibreAdapter`/MapCanvas компонент і спільні `MapState`/`MapMode`/`MapAppearance`/`LayerSelection`; **не монтувати шість MapLibre canvas** для шестикратної матриці дизайну. Режим — camera + style variant, транспортні шари — незалежні state.
- Source-of-truth карти: approved PMTiles/vector style URLs, licensed raster satellite, routing route geometry + instructions, provider-live telemetry тільки з valid timestamps. No `tile.openstreetmap.org` bulk fetch/pack.
- Перемикання стилю: preloading тільки дозволеного невеликого набору важливих assets; відновлювати route, layer selection, selection, driver/passenger markers після `style.load`; зберігати map center/zoom/bearing/selected mode per session, без приватних точної координати в analytics.
- Денні та нічні стилі: separate style definitions/tokens, а не CSS `filter: invert()` усієї карти, що інвертує підписи/супутник/точки. Night satellite = dim/contrast overlays із перевіреною семантикою labels; evaluate provider terms.
- UI state: `SEARCH_BROWSE`, `SEARCH_RESULTS`, `ROUTE_PREVIEW`, `NAVIGATING`, `PICKUP_LIVE`, `OFFLINE_DEGRADED`. Мапа одна, action HUD та допустимі шари міняються за state, не mount іншої карти для кожного сценарію.
- GPS: compass accuracy, unreliable readings smoothing, snap-to-road only when confidence high; predictive vehicle motion strictly bounded by observedAt/receivedAt/TTL; stale indicator; synthetic replay visibly marked *TEST ONLY*.
- Підписи/атрибуція/масштаб: залишати картографічні ліцензійні attribution; не перекривати ETA sheet. Зум-кнопки за потреби на desktop; mobile основне керування жестами + recenter.
- Safe switching: зміна стилю/дня/ночі не скасовує серверну сесію, не очищає обраний Journey або критичну геометрію і не губить voice hints, trip/demand/booking state.

## 9. ЦЕНТРАЛЬНИЙ «+» — QUICK ACTION SHEET (ЧОТИРИ ДІЇ)

`+` відкриває нижній sheet (desktop popup), не окремий шостий tab. Усе в одному ясному переліку:

1. **`Шукаю поїздку · створити заявку`** → `/demands/new` (публікація власного запиту з бюджетом). Щоб не плутати з Home `Шукати поїздку`, дати підпис `Нехай водії запропонують свої умови`.
2. **`Опублікувати поїздку`** → `/offers/new` (дозволений водій, своє авто, вільні місця, ціна).
3. **`Почати навігацію`** → `/navigate` (будь-який користувач; тільки допущений водій може окремо ввімкнути matching).
4. **`Знайти пасажира`** → `/demands` (водій переглядає відкриті заявки та робить пропозицію).

**Розв'язання старої суперечності:** на `Головній` напис `Шукати поїздку` означає знайти вже наявні пропозиції через Search; у `+` напис `Створити заявку / Шукаю поїздку` означає **опублікувати попит**. Підписи дій різні й зрозумілі. Якщо в майбутньому потрібно строго однаковий напис «Шукаю поїздку» на Home/+ — відкривати mini-choice `Знайти готову / Створити заявку`, не робити прихованого різного переходу за однаковим словом.

Не показувати role switch у глобальному header. Для водійських дій: без ролі → `Увімкнути можливість водія`; без придатного фото/авто → `Додати авто`; без необхідного trust level → `Пройти перевірку`, з поверненням до чернетки. Дія «Знайти пасажира» без реального driver eligibility не показує чужих приватних заявок. Gesture close/back/keyboard tested.

## 10. ЗАЯВКА ПАСАЖИРА ТА ЗВОРОТНА БІРЖА (REVERSE MARKETPLACE)

### 10.1 Форма «Створити заявку»

`Звідки`, `Куди`, GPS/map picker, earliest/latest або бажана дата/час, кількість пасажирів, **загальний бюджет за всю заявку** у грн, багаж/супутні вимоги, гнучкість місця/часу, короткий коментар, privacy notice, `Опублікувати заявку`. Бюджет не плутати з ціною за одне місце; показати арифметику «загалом за N осіб». Після submit: `Заявку опубліковано` → `/demands/:id` + `Мої поїздки → Заявки`, доступна edit/cancel з revision bump; сервер валідовує часові вікна, coverage, request TTL й rate limit.

### 10.2 Водій переглядає відкриті заявки

Фільтри `Маршрут/коридор/Дата/Час/Кількість місць/Бюджет/Моя траєкторія`, лише безпечні попередні адреси й неперсональні дані. Карточка показує direction, число людей, total budget, time range, expected detour (+хв/+км тільки якщо обчислені дорожнім router). `Запропонувати` → picker verified vehicle/seat availability, offer total price, час і точка; `Погодитися з бюджетом` або `Запропонувати свою ціну`; valid server proposal.

### 10.3 Торг та підтвердження

У заявці власник бачить усі актуальні пропозиції з даними авто/водія, загальною сумою, часовим вікном, ризиком/умовами, станом ревізії. Дії: `Прийняти`, `Запропонувати іншу суму`, `Відхилити`, `Написати`, `Поскаржитися`. Водій бачить `Переглянути відповідь`, `Прийняти зустрічну`, `Відхилити`. Контрпропозиції формують `revision/version`, expiration; acceptance лише останньої видимої ревізії, transaction reservations, закриття несумісних пропозицій, status+WS+Notification іншим учасникам. Якщо ціна змінилася — explicit reconfirm; не приймати застарілу ціну 200, коли актуальна 150. Результат → booking, trip detail, чат/Live Pickup.

## 11. ПОЇЗДКА ВОДІЯ, АВТО, БАГАТО ПАСАЖИРІВ, НАВІГАЦІЯ

### 11.1 «Опублікувати поїздку»

Форма: дійсна машина із профілю, фото/verification status, місце A→B із точними координатами, початок і дата/час, додаткові зупинки/гнучкість, місця, **вільна ціна за місце**, правила посадки, багаж/тварини/діти/куріння, коментар, `Переглянути на карті`, `Опублікувати`. До public publication перевірити server vehicle seats, status, approval, route distance vs detour, майбутню дату, reason for failure. Дії `Чернетка`, `Зберегти`, `Скасувати`. Після publish перейти у `/trips` → `Заплановані / Я водій`, показати `Редагувати/Скасувати/Знайти пасажира`, але зміна відправлення/ціни/точок за наявності бронювань потребує approval/notifications; не змінювати підтверджені ціни пасажирам мовчки.

### 11.2 Водій просто їде з навігатором

`Почати навігацію` → карта може відкриватися до обраної цілі, компактне поле `Куди їдемо?`, GPS при дозволі, road route. Водій (із перевіреною машиною) окремо вмикає `Підбирати попутників дорогою`; бачить `Місця`, `Максимальний об'їзд хв/км`, `Пауза`, `Вимкнути пошук`. Matching за route corridor попереду поточного місця, перевіряється дорожнім детуром, capacity, time windows, safety. Candidate card `куди / коли / бюджет / +хв / +км / пасажири`, реакції `Пропустити`, `Запропонувати` лише безпечної взаємодії, ніяких довгих форм за кермом. Після підтвердження pickup/drop-off автоматично вставляються в маршрут, новий route revision і повідомлення усім задіяним; не викидати вже домовлені зупинки. У foregound web не обіцяти background GPS; після згортання показати реальний paused state.

### 11.3 Multi-passenger + trip lifecycle

Одна машина може мати кількох пасажирів, кожен бронює N місць на своїх сегментах. Сервер перевіряє місткість **на кожному плечі**, pickup-before-dropoff, stop order, consent, no double-book. UI водія має `Список пасажирів`, `Наступна посадка`, `Проміжні зупинки`, `Я на місці`, `Пасажир сів`, `Пасажира висаджено`, `Завершити`. Пасажир бачить лише свої потрібні деталі й доступну позицію водія, не персональні дані інших пасажирів. Всі переходи server-authoritative, без випадкового запуску/завершення всієї поїздки через одного пасажира.

## 12. «МОЇ ПОЇЗДКИ» — ЦЕНТР УСІХ ОСОБИСТИХ МАРШРУТІВ

**Не перейменовувати цю вкладку на «Маршрут».** Вона об'єднує і пасажирські, і водійські активності. Перший рядок: `Зараз | Заплановані | Історія`. Усередині або за допомогою chips `Усі / Я пасажир / Я водій / Мої заявки / Мої оголошення / Скасовані`; не використовувати водійський глобальний toggle, не роздувати вісім верхніх вкладок. Видимий лічильник `Потрібна дія` для прострочених підтверджень та зустрічних пропозицій, якщо такі існують. Екрани повинні реагувати на реальну серверну машину станів, не лише на client timestamps.

| Стан | Що видно | Головні дії |
|---|---|---|
| Чернетка | не опублікована заявка/поїздка, прогрес | `Продовжити`, `Видалити чернетку` |
| Запланована | дата/час, A→B, місця/ціна, люди, статус, чек-лист | `Деталі`, `Змінити` (якщо дозволено), `Скасувати`, `Чат` |
| Очікує підтвердження | хто має дати відповідь, крайній строк, остання версія умов | `Підтвердити`, `Контрпропозиція`, `Відхилити`, `Написати` |
| Зараз/активна | карта, поточна позиція, наступна зупинка, Live Pickup або рух | `Відкрити маршрут`, `Навігація`, `Повідомлення`, дозволені lifecycle actions |
| Скасована | ким і коли скасовано, refund status лише якщо підтверджений | `Знайти альтернативу`, `Переглянути причину`, `Підтримка` |
| Завершена | підсумки, маршрут, документи за наявності, час/сума | `Відгук`, `Повторити маршрут`, `Поскаржитися` |

**Trip Detail** містить: summary header, статус/дата/role, карту відповідних legs, itinerary stops+ETA+meetings, учасників із privacy guard, details seats, fare and booking capability, дії згідно статусу, блок чату, журнал змін, `Поділитися поїздкою` із безпечним expiring link, доступ до скарги/підтримки. Для пасажира активна вкладка «Мої поїздки» повинна за **одне натискання** вести до власної активної поїздки/Live Pickup; коли активних кілька — показати короткий список.

### 12.1 Live Pickup — під'їзд і посадка

Після підтвердженої угоди окремий екран `Водій прямує до посадки`: карта з точною точкою посадки, орієнтовний час прибуття якщо є оновлення, driver/passenger positions тільки за явної взаємної згоди й активного booking, актуальність кожної позиції, `Я на місці`, `Під'їжджаю`, `Запізнююсь`, `Уточнити точку`, `Написати`, `Зателефонувати` (лише за дозволеним контактним механізмом). Driver бачить наступний pickup; passenger — прибуття водія. Легка анімація ікономашини та реальний ETA; не стверджувати дистанцію 50 м при GPS accuracy 100 м. Тригери наближення типу 500/200/100/50 м — **опційні та вмикаються лише за перевіреною точністю**, відстань не є автоматичним фактом посадки.

Кнопки `Пасажир сів / Почати поїздку` та `Висаджено / Завершити` узгоджені з driver/passenger ролями і серверними state transitions. Після посадки Live Pickup завершує передачу точного GPS за своєю purpose policy. Stale/paused GPS показує `Остання точка ...`, без вигаданої машини, маршрут/бронь залишаються доступними.

### 12.2 Скасування, зміни, Rescue

`Змінити` розбивається на тип параметра: час/адреса/машина/зупинка/ціна/кількість людей. Показати кого зміна стосується і чи потрібна повторна згода. Зміна ціни має revision і explicit approve. `Скасувати` відкриває confirm sheet із наслідками (місця, fee/refund, статус, кому прийде повідомлення) і зрозумілими причинами. Після підтвердження всі сторони одержують status/notif, inventory звільнено атомарно, чат/Journey/GPS/rendezvous переводяться узгоджено.

При відміні або пропущеній пересадці: bottom sheet **`Знайти заміну` / Rescue** із вже перенесеними A/B, датою, кількістю людей, не втрачаючи контексту; кандидатами лише реальні доступні попутки/автобуси/таксі/трансфери тощо, час і можливість встигнути; якщо немає альтернатив — `Опублікувати заявку`, `Змінити час`, `Поділитися`/Підтримка. Не обіцяти гарантовану доставку/страхування без контракту.

### 12.3 Завершення і відгук

Після серверного `completed` → `Оцінити поїздку` (1–5, короткий коментар, релевантні критерії: пунктуальність, чистота, спілкування), `Поскаржитися`, `Показати історію`. Відгук лише учасникам завершеного підтвердженого рейсу, повтор не створює duplicate. Рейтинги не містять фальшивих «97%» та invented averages; якщо немає достатніх даних, `Новий учасник`.

## 13. ПОВІДОМЛЕННЯ І СПОВІЩЕННЯ — ОКРЕМО ВГОРІ

### 13.1 Повідомлення — користувач↔користувач

Верхня іконка bubble веде `/messages`. Inbox із пошуком і діалогами, останнім повідомленням, індикатором непрочитаного, назвою/контекстом trip/demand/proposal, часом, status. Чат `/messages/:id`: avatar/name, trip header → Trip Detail, сторінка з paging і sticky composer, send/retry/dedup, своє/чуже оформлення, day separators, unread/read indicator якщо технічно підтримано, structured negotiation card із ціною/версією/строком і CTA (тільки актуальна). Додатково `Поскаржитися`, `Заблокувати`, `Повернутися до поїздки`, `Подзвонити` за підтриманим privacy-safe каналом, `Закрити`. Чат може відкриватися з бронювання/підтвердження/пропозиції, не тільки з глобального inbox. До домовленості можна дозволити обмежений чат за окремою безпековою політикою, але не відкривати приватні телефони й координати автоматично. Під час водіння текстове поле небажане, показувати зручну безпечну альтернативу або зупинити взаємодію.

### 13.2 Сповіщення — системний inbox

Верхній дзвіночок веде `/notifications`. Категорії `Усі / Потрібна дія / Поїздки / Безпека / Система` лише як **фільтри в inbox**, не вкладки bottom. Події: прийнято/відхилено запит; counteroffer; підтвердження, зміна, скасування booking; призначення зупинки; під'їзд водія; нагадування; перевірка авто/документів; запізнення/Rescue, якщо реально визначені; інцидент. Дії `Відкрити`, `Прочитано`, `Прочитати все`, налаштування уподобань. Клік відкриває відповідний **дозволений** deep link. Badge рахувати лише серверним unread counter; обробляти інший пристрій, web socket reconnect, push deep links, збережений порядок, пустий/просрочений inbox. Chat unread НЕ дублювати в notification unread counter. Системне сповіщення може сигналізувати «Нова пропозиція», але угода підтверджується сервером, не натисканням на toast.

**Push:** тільки opt-in, підтримуване середовище; generic payload без приватних даних. WebSocket foreground і persistent notifications працюють навіть якщо Push unavailable. Web Push/APNs, SMS/email fallback — тільки реально під'єднані канали, без фейкового `Надіслано`.

## 14. «ПРОФІЛЬ», АВТО, РЕЙТИНГ, ВЕРИФІКАЦІЯ, НАЛАШТУВАННЯ

### 14.1 Головна сторінка профілю

Аватар, ім'я/ідентифікатор, phone verification status, rating із кількістю реальних відгуків, рольові capability (`Можу їхати пасажиром` і `Можу пропонувати місця`, не примусовий global switch), «Мої автомобілі», «Верифікація», «Відгуки», «Методи оплати» **лише при під'єднаній PSP**, «Налаштування», «Безпека та приватність», «Підтримка», «Поширити MARSHGO», «Встановити застосунок», «Вийти». Нижня глобальна вкладка залишається `Профіль`, не `Налаштування`. Усі шляхи доступні й зрозумілі на iPhone.

### 14.2 Фотографії та рівні довіри

**Для водія:** обов'язкові фото обличчя і номер авто + мінімум 1 **реальне фото автомобіля**; цільовий UI — **до 3 основних фото авто** (`спереду`, `збоку`, `салон`), з вибором головного; не виставляти водійську пропозицію без достатніх photo/trust prerequisites за затвердженою політикою. **Для пасажира:** фото обличчя опціональне. На картці профілю головний аватар обличчя, swipe/tap перемикає 1–3 фото автомобіля водія з короткими підписами; галерея не збільшує layout до стіни фотографій. Якщо legacy backend допускає до 8 фото, зберігати історичні записи, новий UI показує 3 пріоритетні й керує лімітом відповідно до поточної політики, без видалення чужих уже завантажених фото.

Фото стискати WebP/AVIF+JPEG fallback, strip EXIF, server validation/ownership, приватні evidence-документи через restricted storage, захист від підміни/спаму. Розпізнавання номера і matching photo — автоматичні попередні перевірки, **не видавати за державну юридичну верифікацію без фактичного надійного провайдера**. Базова перевірка номера/фото швидка; підвищена через права/техпаспорт та ручний/офіційний контроль. Badges trust за підтвердженими даними; rating/positive signals: документи, реальні фото, виконані рейси, відгуки; не купований скоринг і не invented five-star.

### 14.3 Автомобілі

`Додати / Редагувати / Активувати / Архівувати`: марка, модель, рік, колір, номер, загальна кількість пасажирських місць, фото 1–3, характеристики, кондиціонер/багаж/тварини/дитяче крісло/зарядка, verification. Не давати створити рейс з архівним авто, перевищити seats або непідтвердженим required trust. При зміні номера/ключових фото/техпаспорта invalidation trust і повторна перевірка. При архівації з активними booking — попередження/обмеження й ясний resolution flow.

### 14.4 Налаштування

`Вигляд` = Системна (default) / Світла / Темна; темна мапа з окремим стилем, не інверсія супутника. `Сповіщення`: per-category opt-in, Push, тихі години, SMS/email only if integrated; `Навігація`: голосові підказки, звук/мова, режим пішки/авто, одиниці, north-up/head-up, show transit/map layers; `Приватність`: location/share controls, блоковані, consent, sessions; `Мова`: Українська default, готовність i18n `en/pl` майбутнє; `Доступність`: reduced motion, контраст, більший текст підтримується системою. Усі зміни мають save/persist/rollback/error indicators; не зберігати паролі й токени у localStorage.

### 14.5 Безпека, підтримка, дані

Сесії/пристрої, `Вийти з цього пристрою`, `Вийти з усіх`, список блокувань, download/export my data, deletion request + cooling-off + cancel request, privacy notices та retention, FAQ, звернення, report user/trip, SOS-екран із **дійсним номером екстреної служби за місцевими правилами**, не вводити в оману про власних диспетчерів 24/7. Support/Reports містить category, опис, attachments за privacy policy, status/timeline, admin escalation. Кнопка телефонного дзвінка учаснику — лише з дозволеного номеру чи через зовнішній provider, не фейкова call UI.

## 15. AUTH, ONBOARDING, PWA ТА ПУБЛІЧНІ СТОРІНКИ

**Перший запуск:** premium welcome з одним чітким `Почати`, 2–3 скромними поясненнями цінності; guest browse/search/read-only можливо за рішенням API (якщо backend потребує auth для search, або реалізувати безпечний read-only endpoint, або чесно показати login gate). **Partner/Carrier Lite (після партнерського підключення):** власний tenant, парк/водії, лінії, зупинки, календар, рейси, ціна/місця, перевірки, скасування, запити й підтвердження, інтеграція по договору. Не показувати customer-facing `Купити квиток` якщо партнер підтримує лише статичний CSV. Адмін може увімкнути INFOBUS за підтвердженим партнерським API; Bolt/Uklon/Uber/інших — лише за офіційним доступом. Аналітика без чату, GPS домівок чи номерів телефонів. Моніторинг/лог доступу модераторів і аудит всіх рішень.

## 18. ТЕХНІЧНІ СТАНИ, ДЖЕРЕЛО ІСТИНИ, ІНТЕГРАЦІЙНІ КОНТРАКТИ

### 18.1 Бізнес-state machines

- **Demand:** `DRAFT → PUBLISHED → MATCHING/PROPOSALS → AGREED/BOOKED → COMPLETED` або `EXPIRED/CANCELLED`; редагування invalidates/revisions dependent offers.
- **Proposal:** `PROPOSED → COUNTERED (version increment) → ACCEPTED/DECLINED/EXPIRED/WITHDRAWN`; stale acceptance 409, server conflict clarity.
- **Offer:** `DRAFT → PUBLISHED → PARTIALLY_BOOKED/FULL → IN_PROGRESS → COMPLETED` або `CANCELLED`; edit constraints and real vehicle eligibility.
- **Booking:** `REQUESTED/PENDING → CONFIRMED → ARRIVING/BOARDING → ACTIVE → COMPLETED`, альтернативно `REJECTED/CANCELLED/NO_SHOW/DISPUTED`; exact enum fit to real API, not two parallel client state machines.
- **Journey:** `PLANNED → PARTIALLY_BOOKED → READY → ACTIVE → COMPLETED`, or `REPLANNING/CANCELLED`; each leg independent status, multimodal tickets not falsely unified.
- **Navigation:** `IDLE → PREVIEW/NO_DESTINATION → GUIDING → PAUSED/DEGRADED/REROUTING → ENDED`; matching opt-in is separate boolean with eligible driver/vehicle guard.
- **Rendezvous:** `PREPARING → APPROACHING → ARRIVED → BOARDED` or `CANCELLED/EXPIRED`; each party's current location available only when permission/status valid.

Transitions must use **existing backend-supported names or versioned migrations**, not invent fresh client booleans inconsistent with server. Seat inventory transactional and per-segment; Idempotency-Key for material actions; booking/cancel/approval/price revision/review/payment events only after DB commit. WSS/outbox signals trigger state re-fetch, not only state persistence. WSS reconnect reconciles with REST snapshot; no duplicate message/booking; refresh-token concurrency safe; old WS closed on session revoke.

### 18.2 Data provenance / capability

Every result shows source, last checked/observed time, price confidence, booking method, availability status, and provider contract capability. Distinguish timetable `SCHEDULE_ONLY` / live `LIVE` / stale `STALE` / unconfigured `NOT_CONFIGURED`. Do not insert hardcoded default providers with `available:true` when credentials/feed missing. Registry and health poller share authoritative backing or provably synchronized state. Multi-server realtime vehicle positions in Redis/shared TTL store or leader worker, not per-process divergent caches. Transit leg planner actually wired to public API, not simply an internal module present. `Arrive by` and walk transfer must be actual planner features before UI claims full multimodal.

### 18.3 Engineering architecture

`MarshGO-Site` owns production React/PWA UI, `MarshGO-Server` owns production API/PostgreSQL/PostGIS/Redis/notifications/booking, `MarshGO-iOS` bundles pinned Site as Capacitor wrapper, `MarshGO` umbrella manages integration/cross-repo release and E2E. **Current main Site and production branch umbrella may differ**, so compare code before changes, move validated features into one release source, no unpinned `main` for release. Existing MapLibre adapters, OSRM contract, PostGIS, Redis, OTP, proposals and chats must be reused. Establish OpenAPI/types shared contract; URL/deep link table verified; shared theme token package; service worker offline shell; object storage credentials never in frontend `VITE_*`.

External feeds: GTFS static (calendar/trip/stops/shapes), GTFS-RT VehiclePositions/TripUpdates/ServiceAlerts, GBFS availability/return zones, ticketing API via INFOBUS or contract partner, optional taxi/transfer/carshare commercial partner; providers can be enabled by city with license/credentials/health. Traffic HERE/TomTom adapters planned but initially **OFF**. Do not create external bookings without supported PSP/partner integration. Domain names/SMS/payment provider and real onboarding launch cities are deployment config, not hardcoded design assumptions.

### 18.4 Status taxonomy

For every essential screen/dynamic card define: `idle/loading/success/empty/error/offline/permission_denied/auth_required/stale/expired/conflict/not_supported`. Show helpful next-step. Use progress skeletons, retry with retained form, no infinite spinners or white blank page. A 500 after successful booking cannot make UI say `бронювання не вдалося` without checking authoritative server idempotent result. No fake success toasts.

## 19. ЯКІСТЬ, ПРИВАТНІСТЬ І ВИМІРЮВАННЯ UX

### 19.1 Адаптивність і доступність

WCAG 2.2 AA, keyboard entire journey, logical focus/visible rings, VoiceOver/TalkBack, touch targets≥44px, zoom 200–400% where appropriate, system dynamic text, error near field, no color-only state, reduced-motion, proper non-text map alternatives, keyboard list of stops/vehicles. iPhone small width 320–430, landscape, iPad, desktop 768–1920, Safari Chrome Firefox WebKit, Capacitor safe-area physical iPhone. Bottom dock never overlaps final CTA or keyboard. User tests: first-time passenger should know where to type, choose modes and book; first-time driver knows how to create ride vs navigate; participant knows where to chat, find trip, respond/confirm, and locate pickup.

### 19.2 Performance

Planning budgets (not measured claims): Web Vitals LCP p75≤2.5s, INP p75≤200ms, CLS p75≤0.1; route list remains responsive midrange hardware; MapLibre lazy import (not blocking auth/Home), WebGL symbols not thousands of React markers, controlled geo request rate, actual tile-source license and fallback; avoid memory leaks/redundant polling across browser tabs, cap WSS subscriptions to viewport, batch deltas and stop hidden/paused fetches. Navigation GPS consumption/battery use measured physical device; no 60-fps heavy 3D meshes. Cold offline app shell by service worker after installed; offline route pack only with licensed tiles; no private verification in CacheStorage.

### 19.3 Trust/security/legal

GDPR-like privacy principles and Ukrainian legal requirements to be reviewed by counsel; minimal location collection, purpose-specific opt-in matching, no indefinite raw GPS history, access-bound exact rendezvous location, private verification docs with short URLs, phone masking, no chat in analytics/push, audit of moderation and settlements. Rate-limit OTP, provider configuration SSRF, strong CORS/CSRF policy for chosen auth, XSS, IDOR booking/chat, stale sessions revoked WS, safe file MIME/size, confidential evidence. Do not auto-publish live Community ride unless driver can legally offer relevant service; distinguish Community cost sharing vs PRO commercial status.

### 19.4 Analytics without sensitive payload

`screen_view`, `bottom_tab_click`, `top_message_click`, `top_notification_click`, `plus_sheet_open`, `quick_action_selected`, `transport_selected`, `provider_selected`, `search_submit`, `search_result_open`, `journey_leg_expand`, `map_mode_changed`, `map_appearance_changed`, `vehicle_tapped`, `stop_tapped`, `offer_created`, `demand_created`, `proposal_countered`, `booking_confirmed`, `trip_opened`, `pickup_arrived`, `trip_completed`, `review_submitted`, `rescue_opened`, `permission_denied`, `offline`, `fatal_ui_error`. Allowed city category and pseudonymous IDs; forbidden exact home/work coordinate, OTP, phone, name, verification materials and private text. Analytics cannot replace server truth.

### Definition of Done

MARSHGO UX/UI готовий тільки якщо пасажир, водій, модератор і перевізник можуть **натискати всі заявлені доступні контролі без тупиків**; кожна дія має правильний endpoint і видимий стан; після refresh/back/device reconnect усе залишається узгодженим; користувач не плутає «Шукати», «Створити заявку», «Створити поїздку», «Навігація»; 12 категорій незмінні; `+` центр нижньої панелі; чати й системні повідомлення розділені; світла/темна карта плавна; транспорт реально рухається лише за справжніми свіжими GPS feed; користувач здатен дістатися потрібної картки/посадки/чату/скасування однією-двома очевидними діями; немає fake booking/price/ETA/payments або непідтвердженого release sign-off.

**Візуальна вимога 10.10.2026:** три надані концепти є затвердженим дизайнерським напрямком для light/dark + 2D/3D/satellite, але їхні намальовані нижні кнопки й будь-які фейкові швидкості/ETA не є функціональною специфікацією. **Остаточний наказ виконавцю:** реалізуй цю специфікацію цілком у існуючих MARSHGO репозиторіях; не замінюй завершення робіт звітом про плани; не знищуй реалізовані функції заради макета; не міняй 12 категорій чи глобальну навігацію без окремого рішення власника.
