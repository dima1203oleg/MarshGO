## 2. БАЧЕННЯ, РОЛІ, ІНВАРІАНТИ

MARSHGO — нейтральний транспортний маркетплейс/навігатор міських і міжміських поїздок України, що порівнює приватні попутки, міський транспорт, маршрутки, автобуси, поїзди, таксі/трансфери, мікромобільність, каршеринг та піші стикування, якщо дані відповідних провайдерів реально підключені.

**Ролі:** гість з обмеженою картою; пасажир; водій (одна особа може мати обидві ролі); оператор перевізника/диспетчер; партнер-провайдер; модератор; адміністратор. Доступ за роллю й ресурсом перевіряє сервер, не JSX.

**Непорушні правила:**
- одна канонічна сутність `Place` та координати WGS84 `[longitude, latitude]`, `placeId`/`stopId` замість порівняння назв;
- один `Journey` із послідовними `JourneyLeg`, одна актуальна версія маршруту, одна система підтверджень/зобов'язань;
- дані карти, маршруту, бронювання, місця посадки та повідомлень синхронізуються за ID та подіями;
- жодної фальшивої «LIVE»-позиції, фальшивого маршруту з неіснуючим транспортом, гарантованого ETA без даних;
- пасажирська ціна приватної попутки визначається водієм, для приватних Community-попуток цільова платформа-комісія **0%**; фінансові правила інших категорій — за договором;
- доступність пропозицій, місць і бронювань підтверджується сервером транзакційно;
- українська локалізація та часовий пояс `Europe/Kyiv`; час у бекенді ISO з TZ, гроші minor units + ISO currency;
- приватність GPS, фото й документів, аудиторський слід критичних змін;
- користувач не вводить одні й ті самі маршрутні дані між розділами.

- production-навігація починається формою замість карти;

## 6. ПОШУК — ЄДИНИЙ ТРАНСПОРТНИЙ ПОШУК

### 6.1 Компоновка

`Звідки` (геолокація або обрана адреса; підтримка точки на карті) → `Куди` → дата/час (`Зараз`, `Відправлення`, `Прибуття до...` там, де підтримується) → пасажири → інтерактивна **мозаїка транспортних типів** → провайдери активних типів → `Знайти маршрут`.

Мозаїку перенести зі старої головної у Пошук; вигляд карток: однакова сітка, лаконічна назва, зрозуміла піктограма, виразний selected-state, не більше 4 колонок на телефоні без мікротексту. Multi-select. `Усі` активне за замовчуванням, при виборі конкретної категорії знімається; повторний `Усі` скидає вузький вибір. `Пішки` — окремий повзунок допустимої довжини пішого стикування, а не обіцянка 0 метрів ходьби на транспорті.

**Порядок популярності:** міські автобуси/маршрутки, попутки, трамваї, тролейбуси, метро, міжміські автобуси, поїзди, таксі, пішки, велосипеди, самокати, каршеринг, трансфери. Додаткові фунікулер, водний транспорт та регіональні mode'и показувати коли релевантні. Не додавати абстрактну категорію `Міський`, що дублює окремі категорії.

**Provider chips:** тільки для вибраних типів, групування `Усі провайдери / Обрані`; пояснення різниці між `Підключено`, `Дані розкладу`, `LIVE`, `Недоступно`; Uklon/Bolt/INFOBUS показувати як броньованих партнерів ЛИШЕ після реальних договорів/ключів/дозволів.

### 6.2 Фільтри

Час; бюджет у гривнях; дозволені пересадки; час пішки; довжина пішого стикування; багаж; тварини; дитяче крісло; місць; доступність; бажаний клас авто; мова, підтвердження і оцінка водія — за реально наявними даними. Фільтри зберігати без блокування першого пошуку. Для непридатної комбінації показувати пояснення.

Окремі явні стани: `IDLE`, `VALIDATING`, `SEARCHING`, `PARTIAL_RESULTS`, `RESULTS`, `EMPTY`, `ERROR`, `STALE`. Не змішувати «немає маршрутів» із «API провайдера недоступний». З частковими джерелами — позначка «Показано доступні джерела, частина операторів недоступна».

## 7. МУЛЬТИМОДАЛЬНИЙ ROUTING ENGINE

### 7.1 Спільна графова модель

Моделювати мережу як time-dependent directed multigraph. Вузли: координати/адреси, платформи/зупинки, транспортні хаби, pickup/dropoff, точки прокату/повернення, в'їзди/виходи, пішохідні конектори. Ребра: рух транспортом, піший перехід, очікування, посадка/висадка, пересадка, трансфер, оренда. Для кожного ребра: `mode`, `providerId`, `serviceId`, `depart/arrive`, `cost`, `currency`, `priceStatus`, `capacity`, `reliability`, `confidence`, `geometry`, `freshness`, `terms`, `bookingCapability`.

**Не з'єднувати** різні зупинки на підставі однакової назви; walking graph потрібно геометрично верифікувати. Маршрут має враховувати реальну точку входу, платформу, буфер на пересадку, ризик затримки, працюючі години, доступність, підйом і спосіб валідації квитка.

### 7.2 Три основні режими ранжування (поверх наявного API)

1. **Оптимальний (BALANCED):** bounded multiobjective Pareto + нормалізоване ранжування ціна/час/пересадки/ризик/пішки. Не винагороджувати невідомий risk як нульовий.
2. **Найшвидший (FASTEST):** мінімальна **door-to-door** тривалість із початковим очікуванням, пішими сегментами, пересадками, фактичною посадкою.
3. **Найдешевший (CHEAPEST):** мінімальна **підтверджена або коректно оцінена** сумарна ціна; нульове/невідоме значення не означає безкоштовно.

`PREMIUM`, `RELIABLE`, `CUSTOM` із наявних серверних стратегій залишаються як розширені налаштування, але верхні три чипи — канонічні. Обчислювати різні результати, а не змінювати лише бейдж.

### 7.3 Pipeline

`SearchRequest` → geocode/canonicalize → provider registry + capability filtering → asynchronous bounded fan-out → нормалізація inventory/offers → time-expanded connection graph → route/walk connectors → transfer feasibility → candidate generation (наприклад, обмежений multi-label shortest path із pruning) → de-duplication → Pareto front → three ranking views → quote refresh → UI.

Примусово вводити timeouts, circuit breakers, rate limits, concurrency quotas й stale cache policy. Завжди версіонувати результати та джерела. Кеш не означає live seat inventory. Навіть якщо planner може теоретично з'єднати до 4–8 сегментів, в UI не видавати маршрут, доки кожен конкретний provider leg і перехід не мають валідного джерела.

### 7.4 Transfer feasibility та ризики

`availableSlack = nextDeparture - estimatedArrival - measuredWalk - transferBuffer - boardingGrace - etaUncertainty`. Якщо від'ємний — маршрут неможливий. Додати перевірку останнього рейсу, роботи станції, можливості посадки/резервації, квиткових тайм-лімітів, різниці часових поясів міжнародних маршрутів, фізичного доступу. Критичний ризик пересадки не видавати як оптимальний без явного попередження.

### 7.5 Rescue

При скасуванні рейсу/водія, затримці, пропущеній пересадці, падінні партнерського статусу або зміні точки посадки — подія змінює `Journey` на `REPLANNING`; запускати пошук від фактичного положення/часу; показати можливі альтернативи та різницю ціни/ETA; **ніколи** не списувати гроші, не бронювати й не переназначати користувача без правил авторизації/згоди. Стан `REPLANNING` не дорівнює автоматично завершеному rescue.

## 8. РЕЗУЛЬТАТИ ПОШУКУ — КАНОН REF_05

**Заголовок пошуку:** адреса старту й адреса фінішу повністю (`вул. ... , номер`) лише **один раз** над списком результатів. На картках їх не повторювати.

**Чипи:** `Оптимальний`, `Найшвидший`, `Найдешевший`. Одна обрана стратегія, стабільний порядок та clear pressed state.

**Картка результату:**
- великий загальний час (напр. `38 хв`) та сумарна вартість (`36 ₴`) з маркуванням `орієнтовно`, `від`, `остаточна`, `невідома` залежно від status;
- кількість пересадок, додаткове піше пересування, при наявності зрозумілий risk indicator;
- одна тонка **смуга у кольорах сегментів**, пропорція сегментів — за часом або узгодженою картою легенди (не міняти принцип від екрану до екрану);
- **КОЖЕН сегмент окремо**: піктограма + тип (`Трамвай`), `15 хв · 15 ₴`; якщо price unknown — `ціна уточнюється`, якщо walking — `0 ₴`; довжина назви стискається, але тривалість/вартість НЕ зникають;
- сердечко для збереження, пересадки, стрілка деталей; типові transport colors не повинні змінюватися між карткою, таймлайном і картою;
- при tap card → повні деталі `Journey` без повторного серверного розрахунку, якщо результат актуальний; при застарінні — revalidate.

**Важливо:** приклад на ескізі з € — дизайнерська помилка, у продукті валюта для UA результатів `₴`, за контрактом UAH. Інші валюти лише для реального міжнародного providerQuote з явною валютою/курсовою політикою; ніколи не перераховувати довільно.

## 9. ДЕТАЛІ МАРШРУТУ — КАНОН REF_02/03

### 9.1 Верх

Мапа з усіма сегментами; `назад`, геолокація, шари; малий handle дозволяє згорнути/розгорнути панель. У header панелі: коротка пара `Звідки → Куди`, загальний час і **загальна ціна**, кількість пересадок, save. Не дублювати цю інформацію в кожному рядку.

### 9.2 Сегментна смуга

Кожному leg на карті, смузі й списку відповідає той самий стабільний колір та іконка. Мапа відображає walking нейтральним пунктиром; трамвай/тролейбус/автобус/поїзд/poputka/самокат/таксі — власними лініями. Не підмінювати справжній geometry straight-line сегментом без позначки.

### 9.3 Timeline

Кожен leg розкривається окремо: mode / lineId / provider / departures / arrivals / duration / fare / availability / source freshness. `Пішки`: відстань, тривалість, напрям до зупинки; `Трамвай`: номер лінії, посадка, наступні/проміжні зупинки, ETA й LIVE тільки якщо є; `Самокат`: оператор, фізична pickup/dropoff зона, оцінений тариф, ризик недоступності; `Попутка`: фото реального авто, водій, рейтинг, місця, точки зустрічі, ціна і кнопка `Забронювати` лише при підтвердженому інвентарі; `Автобус/поїзд`: оператор, номер рейсу, посадка, квиток і інтервал підтвердження. Зупинки і час відкриваються на вимогу, не всі за замовчуванням.

Таймлайн синхронізується з картою: tap сегменту → карта zoom-to-leg, виділяє поточний відрізок, скролює до картки, пам'ятає selection; tap зупинки → маркер/деталі; hover на desktop → коротке highlight; навпаки tap маркера → відповідний leg/зупинка.

### 9.4 CTA

Первинна дія залежить від стану: `Переглянути поїздку`, `Забронювати`, `Купити квиток`, `Почати навігацію до посадки`, `Продовжити`, `Відкрити у провайдера`. Якщо немає інтеграції купівлі, чесно показати зовнішню дію і повернення до MARSHGO. Заборонено показувати власне бронювання там, де доступний лише інформаційний розклад.

## 10. ЄДИНА КАРТА MARSHGO / MAP SHELL

### 10.1 Чотири контексти однієї карти

**Оглядова карта** (перегляд місцевості/пошук); **Карта транспорту** (реальні доступні зупинки/лінії/позиції); **Карта маршруту** (всі пофарбовані legs); **Навігація** (активний сегмент із камерою й HUD). Контекст змінює visibility/layer presets, але геодані, стиль, map registry, взаємодія, gesture semantics — спільні.

**Map state model:** `{basemap, perspective, camera, overlays, selectedJourneyId, selectedLegId, highlightedStopId, followMode, userLocation, dataFreshness}`. При переході `Search → Details → Map → Navigation` передати ID/версію маршруту, не ділитися лише екранним текстом.

### 10.2 Basemap + perspective + overlays

**Basemap тільки два швидкі режими:** `Схема`, `Супутник`. Квадратна окантована **thumbnail-плитка справа внизу** завжди показує протилежний вигляд; один tap — swap із збереженням center/zoom/bearing/pitch/route/overlays/selection. НІКОЛИ не дублювати «Схема/Супутник» у «Шарах». Супутникові ресурси ліцензовані/сконфігуровані. `3D` — незалежний pitch/building toggle, а не третій basemap.

**Шари** — тільки тематичні оверлеї (транспорт/зупинки/трафік/EV/infrastructure/попутки/мікромобільність) з provider registry і статусом свіжості. Не вдавати живі автобуси при GTFS static; при real-time координатах показати `оновлено о HH:MM` і degradation staleness. Типи шарів з урахуванням України: міський автобус, маршрутка, трамвай, тролейбус, метро, приміський/міжміський транспорт і залізниця, taxi/transfer, community, прокат/парковка двоколісного транспорту, carshare, фунікулер/водний транспорт за наявності.

### 10.3 Контроли

Погоджена логічна черговість праворуч: **Шари → 3D → Геолокація → zoom +/− → Звук → Компас (тільки коли bearing≠North, останнє кругле керування) → КВАДРАТ Схема/Супутник в самому низу**. Не примушувати 8 контролів стояти щільним стовпчиком на короткому iPhone: групувати zoom та рідкісні дії у динамічний compact controls popover, геолокацію і квадрат зберігати доступними. Компас не дублювати нативним контролем MapLibre одночасно з власним.

Один узгоджений icon pack, доступна семантика, `aria-label`, touch targets принаймні 44–48 CSS px; для WCAG 2.2 AA додатково перевірити contrast/focus/reduced-motion. Підписи мають лишатися читабельними в темній/світлій темі.

### 10.4 Map renderer

MapLibre GL JS + OSM/vector/PMTiles/self-hosted or contracted style service, style manifest versioning, licensed satellite. Навігаційна карта не повинна повертатися до умовного стилю без вулиць як до повноцінної навігації без чіткого degraded indicator. Повторна заміна style відновлює overlay source/layers і маркери; не монтувати map заново на кожен GPS fix. Всі attribution/license links залишаються.

## 11. АВТОМОБІЛЬНА НАВІГАЦІЯ: PURE DRIVE

### 11.1 Основна UX філософія

Під час руху UI майже зникає; чіткими лишаються: **карта + активний маршрут + стрілка авто + next maneuver + HUD поточної швидкості + перевірений знак speed limit (коли дані є) + компактна ETA-губа**. Додаткові елементи не заважають дорозі. В активній навігації **немає** центрального глобального `+`, немає великої нижньої вкладкової панелі, немає логотипа як великого декоративного елемента, немає пропозицій попутників на півекрана.

**Navigation start:** одразу карта у full-screen із невеликим полем `Куди їдемо?` без автоматично відкритої форми. Пошук адреси — overlay; маршрутні альтернативи — компактна bottom sheet. Після `Розпочати` пошук зверху замінюється маневром.

### 11.2 П'ять станів навігаційного UI

`MAP_IDLE` (пошук); `ROUTE_PREVIEW` (порівняння); `DRIVE_FULL` (контроли відкриті після дії); `DRIVE_PURE` (через ~5 с без взаємодії другорядні контролери згорнуті/візуально погашені); `DRIVE_DETAILS` (губа розгорнута). Додаткові технічні стани `GPS_STALE`, `REROUTING`, `OFFLINE`, `FREE_CAMERA`, `PAUSED`, `ARRIVED`, `ENDED`, `ERROR`.

**Pure Drive:** не «прозорити карту». Прибрати другорядні контролери з поля уваги. Якщо їх залишати видимими, opacity орієнтовно 0.3–0.45 лише для некритичних controls, але інтерактивність/контраст повинні залишатися достатніми. Бажано контекстне приховування, а не невидимі клікабельні місця. При tap у нейтральну ділянку карти контрольна панель проявляється, а при tap на видиму control її дія відбувається **одразу**. Не повертати повний UI при кожному GPS-оновленні. Маневр, safety alerts, speed HUD і ETA не затухають.

### 11.3 Банер маневру

На safe area верхнього екрану: темний/контрастний rounded banner з білою піктограмою типу turn, великим `Через 300 м`, наступним рядком `Поверніть праворуч` і точною назвою дороги, якщо вона відома. Lane guidance при достовірних maneuvers. Мітки street/camera не повинні перекриватися. В `maneuvers=[]` — чесний `Слідуйте маршрутом`, не fake TURN. Production full turn-by-turn не можна випускати, доки maneuvers не реалізовано. Голос українською з ідентичного маршруту/routeVersion; кнопка sound показує дійсний стан, без неактивної обіцянки.

### 11.4 Швидкість і знак обмеження

Нижній лівий HUD: **поточна швидкість** із GPS `speedMps * 3.6`, згладжена без приховування застарілих samples; `72 км/год` — лише приклад. Якщо `speedMps` невалідна/відсутня — `—` та ненав'язлива індикація «недоступно», не вигадувати число. Поруч нормативний вигляд знака із червоним обідком і значенням тільки із правомірного джерела `SpeedLimitProvider`, map-matching на конкретну дорогу + напрям + timestamp/quality; при невідомому ліміті знак **ховати**, не припускати 50/90. При перевищенні — м'який контрастний сигнал без миготіння; конфігурація порогу й голосу. За правової невизначеності країни правило speed sign не виводити до доказу коректності.

### 11.5 Нижня губа

**Collapsed:** низька плаваюча панель із drag handle, `24 хв · 10 км · 17:24`; її висота мала, не перешкоджає карті, safe area iPhone враховано; час із валідної ETA, без трафіку не видавати як traffic-aware. **Expanded:** заголовок `Маршрут до ...`, summary, ряди `Огляд маршруту`, `Пошук уздовж маршруту`, `Налаштування`, opt-in `Підбирати попутників дорогою` — у розділі нижче; **велика окрема контурна/червона кнопка `Завершити навігацію` внизу** з підтвердженням. **Full detail:** список маневрів, зупинки, слоти для перевіреної технічної інформації. Губу можна згорнути і свайпом, і натисканням handle; при відкритті карта змінює safe padding, vehicle marker не ховається за шторкою.

### 11.6 GPS/reroute/camera

`OVERVIEW`, `FOLLOW`, `FOLLOW_HEADING`, `MANEUVER`, `FREE`, `RECENTER_PENDING`. Адаптивні zoom/pitch за складністю маневру й швидкістю; плавний heading із фільтрацією шуму, не обертати карту на місці. Відхилення: послідовні якісні fixes + похибка GPS + гістерезис, потім reroute на актуальну підтверджену точку. При reroute атомарно міняти geometry/maneuvers/ETA/waypoints/routeVersion; скасовувати race старих відповідей. Оффлайн/старий GPS/visibility в web: чесний стан. Не обіцяти гарантовану фонову навігацію в Safari/WKWebView без окремих native entitlement/capabilities.

## 12. КАРТА ТРАНСПОРТУ: LIVE, РОЗКЛАД, ПОДІЇ

`Карта транспорту` — повноекранна карта з пошуком зупинки/лінії, перемикачами типів, доступними постачальниками, transport overlays. Показує: лінії, зупинки, маршрути, пасажирські pickup points, доступну мікромобільність/парковки, коли реально підключено.

**Фактично різні рівні:** `LIVE_POSITION`, `REALTIME_ETA`, `SCHEDULED`, `STATIC_INFRASTRUCTURE`, `STALE`, `UNKNOWN`, `PROVIDER_BLOCKED`. При відсутності vehicle positions заборонено малювати плавно рухомий «живий» автобус від розкладу. Для GTFS Static/RT версіонувати trip/stop/station relationships; опрацьовувати timezone й service calendars. Feed freshness SLA специфічне для provider, stale badge і cutoff.

**Тап на автобус:** номер/напрям/найближча зупинка/час із коректним типом оцінки/джерело; `Прокласти до зупинки` → створення walking JourneyLeg або окрема навігація до boarding, не окремий несумісний маршрут. Tap pickup ride → offer detail. Tap EV charger → сервіс/стан/доступність за даними провайдера.

## 13. ПУБЛІКАЦІЯ ТА REVERSE MARKETPLACE

### 13.1 Глобальне `Опублікувати`

Невелика модалка з двома варіантами: `Пропоную поїздку` (водій); `Шукаю транспорт` (пасажир), потім цільовий flow без зайвих питань. Публікація не повинна вимагати повторного вибору `Звідки/Куди`, якщо такі точки вже є в JourneyContext; користувач може змінити їх.

### 13.2 Водійський офер

Поля: старт і фініш як geocoder place; дата/час; точки посадки/проміжні pickup із забороною недоступних зупинок; фото фактичного авто з профілю, число місць, правила багаж/тварини, довільна ціна **за місце**, валюта, примітка, підтвердження маршруту OSRM; попередній перегляд полілінії та приблизної тривалості; публікація після серверної валідації перевіреного авто/фото й коректності майбутнього часу. Не трактувати будь-який автопошук шляху як опубліковану пропозицію.

### 13.3 Попит пасажира

Точка A/B, бажаний інтервал часу, кількість пасажирів, бюджет (за місце чи за всіх), вимоги; карта corridor/proximity; серверна видимість для відповідних водіїв. Контрпропозиції з ціною/часом/авто, історія версій, згода сторін, ідемпотентне підтвердження бронювання. `Interest` не дорівнює `booking`.

### 13.4 Попутники по дорозі (navigation matching)

Вимкнено за замовчуванням, явний opt-in водія, потрібне verified vehicle та вільні місця. Заявки за географічним коридором **плюс перевірка detour route** із pickup-before-dropoff, сидіннями й часом. У Pure Drive тільки дрібна нотифікація/звук за дозволом; ціна/торг/підтвердження — лише після безпечної зупинки/paused state. Після passenger confirmation і negotiated booking сервер оновлює stops/ETA/routeVersion й надсилає подію; на карті з'являються pickup/dropoff. Після зміни маршруту повторна явна згода на matching за відповідним правилом сесії.

## 14. БРОНЮВАННЯ, КВИТКИ, ПОЇЗДКИ, ПЛАТЕЖІ

**Booking state machine:** `DRAFT → QUOTED → HOLD_PENDING → PENDING → CONFIRMED → IN_PROGRESS → COMPLETED`; альтернативні `FAILED`, `EXPIRED`, `CANCELLED`, `DISPUTED`, `REFUNDED` (лише де застосовно). Не всі провайдери дають HOLD, тому можливості визначаються contracts; квитковий provider може мати власну подію issuance.

**Жорстко серверні:** підтвердження інвентарю, блокування місць, idempotency key, право доступу, ціна/fee snapshot, дедлайни оплати, статус партнера, refund policies; UI не зменшує доступні місця самостійно. 0% комісія приватної попутки означає саме відсутність сервісної комісії MARSHGO для цього виду, але сторонній processing fee показувати окремо, якщо виникає за договором.

**Квиток:** справжній ID/QR лише від дозволеного backend/provider, маршрут, відправлення/прибуття, місце/місця, посадка, статус, оплата, умови повернення, кнопка карта/як дістатися, повідомлення перевізнику; при зовнішньому checkout повернення тільки з server-confirmed status, не вірити client callback. Не фальсифікувати QR.

**Мої поїздки:** майбутні/активні/архів/опубліковані/запити; синхронізація hero-квитків, чатів, навігації, rendezvous/ETA. При скасуванні — `REPLANNING`, rescue flow з підтвердженням нової ціни; історичні платежі не стирати. Маршрут у деталях booking — той самий Journey/Leg version.

**Платежі:** PaymentProvider із `createIntent`, `confirmWebhook`, `refund`, `reconcile`; signed webhooks, PCI-scope мінімізувати, платежі тільки з фактичним договором і secrets у server; якщо платіжна інтеграція відсутня, немає активної кнопки «Сплатити в MARSHGO».

## 15. ПРОФІЛЬ / ВЕРИФІКАЦІЯ / РЕЙТИНГ

**Секції профілю:** персональні дані; мої поїздки/бронювання; збережені маршрути/місця; роль пасажира/водія; мої автомобілі; верифікація; оплата й квитанції (коли підключено); нотифікації/чат; приватність/дозволи; налаштування теми/карти/навігації; допомога й підтримка; експорт даних/видалення аккаунту; admin за роллю.

**Автомобіль:** державний номер з відповідною приватністю, 1+ реальне фото (рекомендовано спереду, збоку, салон), фото обличчя водія; пасажирський аватар опціональний. Розгортання профілю за tap/gesture для перегляду автомобіля; не змінювати аватар обличчя на номерний знак у головному header.

**Ступені підтвердження:** `Unverified / Photos supplied / Basic data checked / Documents reviewed / Verified`. Завантаження фото та прості автоматичні перевірки — швидкі, але **не називати юридичною верифікацією** без підтвердження прав/техпаспорту відповідним trusted process. Поточні server endpoints уже мають захищені evidence/upload/review; при майбутній авто-верифікації не обходити їхній status/authority. Відображати badge строго зі server state.

**Рейтинг:** після фактично завершеної поїздки, anti-sybil/anti-review-spam; прозоро відокремити reviews від verification trust badges. Не придумувати бали, якщо немає даних.

## 16. ПОВІДОМЛЕННЯ / НОТИФІКАЦІЇ / БЕЗПЕКА

Єдиний persisted inbox. Контекстні чати для demand/proposal/booking, з правами сторін і block rules. Deep-link повідомлення → відповідний Journey/Booking/Conversation, після повернення маршрутна сесія не повинна помилково завершитися. Realtime — Redis/WebSocket/outbox у сервері, дедуплікація eventId та упорядкування aggregateVersion, reconnect. При push відсутній — UI показує лише in-app статус, не обіцяє повідомлення у фоні.

Шаблони подій: пропозиція/контрпропозиція, прийняття, бронювання, ticket issued, upcoming boarding, driver approaching, change of stop, reroute, cancellation, missed transfer, rescue choices, payment, refund, moderation. Приватний контент повідомлень приховувати на lock screen за opt-in.

**Safety:** заблоковані користувачі не можуть отримувати невідповідні персональні дані через прямий API, чат, matching або карти. Дорожні popups/інтерактивні повідомлення не затуляють маневр під час руху. Не дозволяти вводити текст/торгувати/бронювати водієві під час руху.

## 17. DATA MODEL: СЕРВЕРНА КАНОНІЗАЦІЯ

У нових `shared/contracts` описати й версіонувати:

- `Place` (placeId, officialName, displayLabel, WGS84 point, address components, precision/source);
- `Stop/Station/Platform` (canonical provider IDs, locations, access flags, last verified);
- `Provider` (id/modes/geographies/availability/capabilities/licensing/health/lastSynced);
- `TripOffer` (driver/car/photos/route/schedule/price/inventory/visibility);
- `PassengerDemand`, `Proposal`, `ProposalRevision`;
- `Journey` (id, owner, version, departure, arrival, total cost status, risk, route alternatives);
- `JourneyLeg` (mode/provider/geometry/timing/boarding/dropoff/status/price/booking capability);
- `TransferConnection` (measured walk, buffer, ETA uncertainty);
- `NavigationSession` (sessionId/routeVersion/active leg/GPS freshness/matchingOptIn);
- `NavigationRoute` (polyline6/bounds/maneuvers/ETA/waypoints/source);
- `Booking`, `Ticket`, `Payment`, `Refund`, `Rendezvous`, `RescuePlan`;
- `Message`, `Notification`, `DomainEvent`, `AuditEvent`;
- `Vehicle`, `VehiclePhoto`, `VerificationRecord`, `UserRole`;
- `ProviderQuote` з `currency`, `minorUnits`, `LOCKED/ESTIMATED/DYNAMIC/UNKNOWN`, TTL;
- `RealtimePosition` зі source/lastUpdated/accuracy/status.

**Version invariants:** API objects мають resource ID; `Journey.version`, `NavigationSession.routeVersion` та outbox aggregateVersion виключають перезапис пізньою старою відповіддю. Не допускати PII в telemetry та публічних deep links. Приватні автомобільні фото/документи — signed URLs TTL, перевірка MIME/розміру/signature, RBAC, шифрування.

## 18. КЛЮЧОВІ ІНТЕГРАЦІЙНІ СЦЕНАРІЇ (ОДИН FLOW)

**S1. Пошук → деталізація → бронювання:** геокодер встановлює origin/destination → backend повертає Journey ID з чіткими legs/providers/freshness → tap leg виділяє карту → quote refresh → atomic booking → ticket → Home hero → MyTrips. Без повторного вводу маршруту.

**S2. Попутка → навігація водія:** driver offer (car verified, price, seats, real geometry) → booking confirmed → pickup/dropoff waypoints → NavigationSession з routeVersion → GPS/ETA → rendezvous → trip lifecycle → review.

**S3. Трамвай + попутка:** transit line/stop arrival → walking connector → booking-dependent rideshare leg → ризик пересадки → на detail tap «До посадки» → GPS walking navigation → зміни наступного leg синхронізуються з чатом і квитком.

**S4. Рух → попутник:** активний водій вручну вмикає matching → PostGIS corridor + route detour → low-interruption candidate → driver pause/interest → passenger confirmation → price proposal → booking → server stops optimization → realtime `navigation.route-updated` → marker/ETA update.

**S5. Скасування:** driver/provider cancel → booking state + Journey REPLANNING → подія в inbox & hero → rescue search (свіжа доступність, не репліка старої) → explicit rebooking → нова поїздка й нові навігаційні waypoint'и.

**S6. Реальний автобус:** provider GTFS real-time position → карта транспортних шарів зі статусом LIVE і timestamp → tap vehicle → stop ETA → `Прокласти до зупинки` → той самий JourneyContext; при feed stale «стан застарів», а не анімований автобус.

**S7. Прохід по застосунку під навігацією:** користувач відкриває чат/квиток із навігації → sessionId на сервері існує → UI route context зберігається → при поверненні відновити на підставі свіжого GPS, а не припускати фонового трекінгу браузером.


## 18A. ОБОВ’ЯЗКОВА МАТРИЦЯ ЗВ’ЯЗКІВ МІЖ КАРТОЮ ТА ВСІЄЮ ПРОГРАМОЮ

**Це ключова частина ТЗ.** Жоден екран, який має транспортний або географічний зміст, не може існувати як відокремлений набір намальованих маршрутів без ID, координат, прав доступу та синхронізації із сервером. Різні контексти карти можуть мати різну композицію, але використовують **одні географічні й маршрутні контракти**. UI-компонент карти не є самостійним джерелом істини про квитки, ціни або доступність.

| Розділ | Інтеграція з картою | Двостороння дія / обов'язкова синхронізація |
|---|---|---|
| Головна | компактне місце/місто, hero активної поїздки | tap ticket → map обраного Journey + status; повернення без втрати вибору |
| Пошук | точки A/B, GPS, вибір на карті, транспортна мозаїка | зміна точки на карті оновлює поля; зміна поля оновлює pin; searchRequest має стабільні place IDs |
| Результати | preview геометрії маршруту під час tap картки | вибрана картка підсвічує route; альтернативи нейтральні; карта та список мають однаковий journeyId/version |
| Деталі Journey | карта сегментів із walking connectors / stops | tap leg ↔ map highlight + панель leg; tap stop ↔ відповідна зупинка в timeline |
| Попутки | маршрут офера, реальне авто, точки pickup/dropoff | tap offer → карта офера; booking змінює seat inventory, не підмінює geometry |
| Reverse marketplace | demand origin/destination, допустимі meeting points | контрпропозиція оновлює часовий і ціновий стан; route compatibility лише за серверним detour |
| Міський транспорт | lines/stops/vehicles з рівнем свіжості | tap vehicle → line/next stop; tap `Дістатися` → пішохідний segment у контексті Journey |
| Міжміські автобуси/поїзди | термінали/станції, платформи, доступні рейси | реальна stop identity й schedule/serviceDate; ticket зв'язаний з providerBookingId |
| Таксі/трансфер | pickup і destination, fare quote, ETA/availability | deep link або booking — залежно від справжнього capability; жодного фальшивого власного підтвердження |
| Самокати/велосипеди | дозволені pickup/dropoff zones, парковки | перехід від walking leg до rental leg тільки з реальним operator availability |
| Каршеринг | дозволена зона, автомобіль і стан, паркінг | geofence та driving leg із реальними terms; booking capability тільки за партнером |
| Навігація | поточна версія route + маневри + speed/limit + ETA | reroute змінює routeVersion атомарно; інші екрани отримують нові координати та час |
| Водійські попутники в дорозі | corridor / кандидати / pickup / dropoff | interest → confirmation → proposal → booking → revised stops/map; без автоматичного accept |
| Мої поїздки | active/upcoming/completed, карта pickup/dropoff | бронювання, затримка, скасування та rescue оновлюють badges й карту |
| Квиток / hero | локація посадки, QR/референс тільки за провайдером | `Маршрут до посадки` відкриває navigation без втрати ticket; скан не замінює confirmation |
| Повідомлення | context-link на Journey/Booking/Offer/Stop | tap message-link відкриває авторизований ресурс + map focus; chat сам не змінює бронювання |
| Сповіщення | локації подій, пересадка, посадка | tap event → актуальний routeVersion/status; невдале підтвердження показує пояснення |
| Профіль | збережені місця, авто, недавні поїздки | tap home/work/recent → canonical Place; vehicle settings впливають на дозволені route profiles |
| Зарядні станції | точки/роз'єми/наявність лише за джерелом | маршрут до зарядки; динамічний SoC лише з дозволеного джерела, без вигаданого залишку |
| Адмінка | feed coverage, geofence, provider health, incidents | зміна провайдера інвалідовує кеш шарів/пошуку; аудит змін та safe rollout |
| iOS/PWA | shared map UI, safe area, geolocation capability | одна логіка IDs/events; нативні функції через capability adapters, без fork бізнес-моделі |

**Приймання матриці:** для кожного рядка розробник створює інтеграційний сценарій, event trace, frontend test і backend authorization/contract test. Заборонено вважати екран завершеним лише через гарну статичну карту.

## 18B. CANONICAL JOURNEY CONTEXT І СИНХРОНІЗАЦІЯ ДВОХ НАПРЯМІВ

Цільова модель контексту (псевдоконтракт для адаптації до наявних типів, не готове серверне API):

```ts
type JourneyContext = {
  origin: { placeId: string; coordinates: [number, number]; label: string } | null;
  destination: { placeId: string; coordinates: [number, number]; label: string } | null;
  search: { departureAt?: string; passengers: number; selectedModes: string[]; providerIds: string[]; strategy: 'BALANCED'|'FASTEST'|'CHEAPEST' };
  selectedJourney: { id: string; version: number } | null;
  selectedLegId: string | null;
  selectedStopId: string | null;
  bookingIds: string[];
  activeNavigationSessionId: string | null;
  map: { basemap: 'SCHEME'|'SATELLITE'; perspective: '2D'|'3D'; highlightedRouteId?: string; followMode?: string };
  provenance: { source: string; fetchedAt?: string; stale: boolean };
};
```

Зберігати окремо **серверний об'єкт маршруту** (авторитетний), **локальний UI selection** (тимчасовий) і **GPS stream** (тимчасовий, приватний). Під час переходу між екранами не копіювати цілий масив stop/geometry в URL або localStorage; передавати ідентифікатори й за потреби відновлювати з API. Один route ID може мати багато версій. Всі відповіді з `version < currentVersion` і всі realtime-події не для поточного aggregate відхиляються або примушують safe refresh.

**Команди UI:** `SELECT_PLACE`, `CHANGE_ENDPOINT`, `SELECT_JOURNEY`, `SELECT_LEG`, `SELECT_STOP`, `FOCUS_MAP`, `START_LEG_NAVIGATION`, `START_DRIVE`, `RETURN_TO_ACTIVE_JOURNEY`, `SHOW_BOOKING`, `OPEN_CONTEXT_MESSAGE`. Кожна команда має route transition, permission check і чітку fallback поведінку. `SELECT_LEG` не запускає бронювання; `SHOW_BOOKING` не змінює server booking status.

**Приклад транзакційної синхронізації:** сервер підтвердив Community booking → записав booking/inventory і outbox event → ticket generator (тільки якщо застосовно) → frontend отримав подію або після reconnect перечитав booking/Journey → Home hero, MyTrips, карта точки посадки та message context показують **те саме підтвердження**, а не різні кешовані стани.

## 18C. НАСКРІЗНІ СЦЕНАРІЇ З МУЛЬТИМОДАЛЬНИМИ ПЕРЕСАДКАМИ

**Passenger 1:** Search `Мале Голоско → вул. Сихівська` → три серверні стратегії → один обраний Journey `WALK → TRAM → SCOOTER → COMMUNITY → BUS → WALK` **тільки якщо кожен leg доступний і підтверджений реальним джерелом** → карта малює шість сегментів і час/вартість кожного → пасажир бронює лише Community leg → Journey і ticket залишаються зв'язаними → GPS-навігація до трамвайної зупинки → реальний transit reminder → точка посадки на попутку → автобус → піший фініш. Якщо сервіс відсутній, UI показує часткову пропозицію і не синтезує фіктивний маршрут.

**Passenger 2:** заміна перевізником автобуса чи скасування попутки → `Journey REPLANNING`, значок у Home hero, MyTrips і деталях; нотифікація веде на обраний Journey → rescue з фактичної нової позиції + нового часу, re-quote, явне підтвердження нового бронювання, перерахунок усіх подальших пересадок, збереження історії операцій.

**Driver:** публікує офер з авто й реальною геометрією → пасажир бронює → водій запускає Pure Drive → зупинки посадки/висадки синхронізуються з Booking → на дорозі водій opt-in на matching → безпечна пропозиція → після погодження ціни сервер транзакційно створює booking та оновлює waypoint sequence → reroute навігатора → змінюється ETA усіх зацікавлених користувачів; старі повідомлення не перезаписують поточний стан.

**Transit:** user taps зупинку на карті → бачить напрямки і рівень довіри `LIVE/SCHEDULE/STALE` → `Прокласти до зупинки` → авторитетний geocoded target, walking route з реального провайдера; якщо рейс запізнюється, сервер перевіряє ризик пересадки; без нового плану показує попередження, не вигадує автоматичну заміну.

## 19. PROVIDER REGISTRY + АДМІНКА

Окремий provider registry у `MarshGO-Server` із модульними adapter/integration packages. Поля: id, категорії транспорту, coverage, capabilities `SEARCH/QUOTE/BOOK/CANCEL/STATUS/REALTIME`, live/non-live, feed freshness, version, licenses, attribution, rate limit, circuit breaker, credentials reference, enable flags per geography, operational health. **Адмінка**: увімкнути/вимкнути provider, тариф, регіон, шари, GTFS-feed, модерацію, відстежувати помилки, latency, падіння підтверджень, commercial SLA.

**Пріоритети партнерів до масштабного GO:** принаймні 1 квитковий API-партнер (наприклад INFOBUS за договором), 3–5 таксопарків/диспетчерських, 10–20 автобусних/маршрутних операторів з даними й правом їх використовувати. Для міського транспорту — GTFS Schedule/Realtime з офіційних муніципальних feeds, лише за фактичною доступністю. Закриті платформи (напр. Uber/Bolt/Uklon) НЕ скрапити або імітувати API. Зареєструвати партнерські blockers і UX fallback до офіційного зовнішнього booking URL, якщо дозволено. Партнерська комісія/відсоток — лише з підписаних умов, попередня цифра не гарантована.

## 20. ДИЗАЙН-СИСТЕМА І ADAPTIVE UI

**Ідентичність:** стримана Apple-like ясність, але власний MARSHGO; нейтральна карта й контрастний синій маршрут. Базові токени: blue `#2563EB`, dark navy `#101827`, ink `#14233B`, white `#FFFFFF`, emerald для успішних статусів, amber для неповних даних, danger red тільки для критичних/stop; другорядні фон/контури рівняти з WCAG. Шрифти SF Pro/system із кирилицею, system fallbacks; інтерфейс українською, без декоративних величезних заголовків.

**Два рівні UI:** low-density **Pure Drive**; high-information **Journey Details/Results**. Темна і світла тема + `Системна` за замовчуванням, перемикання без втрати маршруту. Темні screenshots є прикладом night results, а не вимогою примусово темної теми для всіх.

## 23. PRIVACY / SECURITY / COMPLIANCE

GPS лише за явним дозволом та реальним станом сесії; мінімізувати точні координати й retention. Експозиція авто/водія до confirmed booking — за політикою приватності. Верифікаційні докази недоступні іншим користувачам. JWT/refresh-cookie lifecycle, CSRF/CORS/CSP, SSRF guard для партнерських URLs, input validation, rate limits, tamper-proof price, audit log дій admin/booking/refund/verification, encryption in transit/at rest, backups, restore drills. API secrets — сервер або provider secrets store, жодних приватних ключів у `VITE_*`.

Структуровані логи без номерів документів/повних телефонів/сирих координат за замовчуванням. Доступна функція експорту/видалення даних із retention exceptions юридичних транзакцій. Перевірити відповідність локальному законодавству про перевезення, оформлення продажу квитків, платіжні сервіси та геодані до запуску.

## 24. OFFLINE, DEGRADED, НЕКОМПЛЕКТНІ ДАНІ

Єдиний UX-підхід: `AVAILABLE / ESTIMATED / STALE / UNAVAILABLE / PERMISSION_REQUIRED / PROVIDER_BLOCKED`. Карта без тайлів ≠ повноцінна навігація, кеш маршруту ≠ офлайн reroute, статичний розклад ≠ live GPS, оцінена ціна ≠ confirmed fare, matching interest ≠ booking. Відображати джерело, час оновлення та scope невизначеності. Для офлайн зберігати лише мінімально необхідні дані та керовано очищати; права на кеш тайлів визначаються ліцензією провайдера.

У разі збою частини API результати з доступних джерел залишаються, але мають `partial` reason; не повертати «0 ₴» чи «0 хв» замість unknown. При втраті GPS не продовжувати анімувати marker уздовж маршруту як реальне переміщення.

## 26A. НЕЛІНІЙНІ ТЕСТИ ВЗАЄМОДІЇ МІЖ МОДУЛЯМИ

Перевірити сценарії не лише «щасливого шляху», а конкурентні зміни:

1. Водій на карті після підтвердження booking отримує новий pickup, поки вручну відкрито режим FREE CAMERA; routeVersion оновлюється, але користувацьке ручне зміщення не скидається непередбачувано.
2. Пасажир має два заброньовані legs, один скасовано; інший квиток не зникає, сумарна ціна не показує скасоване як активне, а Rescue не бронює за користувача.
3. Пасажир одночасно натискає «Забронювати» у вебі й на iPhone; сервер створює не більше одного booking для одного idempotency key і правильно зменшує capacity.
4. Користувач відкриває deep link до чужого Journey/Booking/Chat: доступ забороняється сервером, карта не видає приватних координат.
5. GTFS-RT запізнюється, але Static feed наявний: LIVE vehicle прибирається/маркується STALE; попередня карта залишається придатною для розкладу з коректним статусом.
6. Провайдер повертає інвентар, потім помилку на quote: результат показує 'Не можна забронювати зараз', без вигаданої ціни і без кнопки підтвердження.
7. Втрата мережі після натискання `Завершити навігацію`: не повідомляти про серверне завершення, доки воно не підтверджене; локальний трекінг/відсилання координат зупинити за безпечною політикою; після reconnect синхронізувати authoritative status.
8. Відкриття Messages або Ticket під час активної навігації: навігаційна сесія не скидається; повернення показує свіжу або чесно застарілу GPS-позицію, не симулює продовження в фоні.
9. iPhone 15 Pro Max/малий iPhone landscape: safe areas, клавіатура, картографічні контролери, speed HUD, нижня губа й прев'ю-супутник не перекривають маневр та одне одного.
10. Сортування FASTEST/CHEAPEST/BALANCED спирається на door-to-door і сумарну відому ціну; unknown fare не трактувати як 0; якщо лише Community інтеграція — інші mode'и не підставляти зі зображення.
11. Оновлення точок A/B у Search змінює маркери карти й скидає обраний застарілий Journey; натомість звичайний basemap switch не скидає Journey, Leg selection і Provider filters.
12. Компас з'являється лише при non-zero bearing; у North-Up його немає. Basemap квадрат показує протилежний режим, а у 'Шарах' не може з'явитися duplicate basemap menu.

## 26B. PERFORMANCE / OBSERVABILITY / RELEASE QUALITY

**UX budget, цілі до профілювання на цільових пристроях:** основна навігація підтримує плавну карту без систематичних лагів; інтенсивність GPS-подій не спричиняє повний React re-render; використати sampling telemetry для `navigation_start_success`, `maneuver_source_missing`, `GPS_STALE`, `replan_latency`, `provider_partial`, `quote_expired`, `booking_conflict`, `map_style_switch`, `app_resume`, `feed_stale`, `ticket_invalidated`. Час до готовності карти, час видачі маршруту, помилки API, батарея/пам'ять й FPS вимірювати на реальних пристроях у визначеному профілі тестової мережі. Не встановлювати довільний поріг «60 FPS на всіх телефонах» як гарантований факт.

**Failure ownership:** кожен критичний user flow має власника frontend, власника backend, потрібне джерело, автоматичні тести, fallback стан, SLO/alert після впровадження observability і пункт для production gate. У реліз-маніфесті вказати commit SHA всіх чотирьох repo, версію contracts/migrations, feature flags, map style assets та зовнішніх API capability. Будь-яка функція зі статусом `BLOCKED_EXTERNAL` не повинна бути представлена користувачу як доступна.
