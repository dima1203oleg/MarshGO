# MARSHGO — тези єдиного плану аудиту
Дата: 18.10.2026 · Статус: попередній інвентаризаційний аудит, **не дозвіл на злиття або реліз**.

## Що підтверджено в GitHub
- **7 репозиторіїв**: `MarshGO`, `MarshGO2`, `MarshGO-Server`, `MarshGO-Site`, `MarshGO-iOS`, `MarshGO-Admin`, `MarshGO-Partner`.
- **30 відкритих PR** за перевіреним знімком: відповідно 4, 0, 8, 8, 6, 2, 2.
- PR пов'язані залежностями: деякі мають за базу не `main`, а інші робочі гілки. Їх не можна безпечно зливати без перевірки порядку й конфліктів.
- У `MarshGO/RELEASE_MANIFEST.json` перевірені кандидати мають статус `NOT_RELEASED`, `production_ready: false`. Реальний стан production, доступ до інфраструктури та deployed SHA **не підтверджені**.
- Правила передачі контексту між вікнами Codex додані до `AGENTS.md` у гілках `feature/codex-ownership-guidance` для Server/Site/iOS; вони **ще не в `main`**.

## Короткий план
1. **Збереження:** не видаляти файли, гілки, PR або історію; **нічого не архівувати**, не виконувати force-push, автоматичний merge чи деплой без окремого рішення власника. Зафіксувати вихідні SHA.
2. **Єдиний координатор:** один головний діалог Codex у поточному проєкті. Нові допоміжні завдання — переважно read-only, зі звітом у головний діалог і Git; діалоги не вважати спільною пам'яттю.
3. **Повний аудит 7 репозиторіїв / 30 PR:** для кожної гілки визначити призначення, змінені файли, залежності, тести, конфлікти та корисні унікальні функції. Відокремити факти від припущень.
4. **Ролі:** Server — API/БД; Site — веб/PWA/навігація; iOS — нативна оболонка; Admin — адмінпанель; Partner — кабінет партнерів; MarshGO — перевірити як координатор інтеграції/релізів; MarshGO2 — лише перевірити на унікальні напрацювання, **без архівації**.
5. **План інтеграції:** скласти таблицю «залишити / вибірково перенести / відкласти / кандидат на архів (лише рекомендація)» з поясненням та посиланнями на PR/SHA. Не вибирати гілку-основу навмання. Об'єднувати лише погоджені зміни у відокремлених інтеграційних гілках.
6. **Перевірки й економія Codex:** швидкі цільові тести під час змін; повні CI/E2E та iOS-збірка у контрольних точках і перед релізом. Компіляція ≠ production-деплой. Не перечитувати великі журнали успішних збірок без потреби.
7. **Контроль релізу:** звірити точні Server/Site/iOS commit SHA у release manifest; окремо перевірити фактично розгорнуту версію, міграції, staging, відкат. `NOT_RELEASED` не перетворювати на `RELEASED` без доказів.
8. **Передача між сесіями:** наприкінці завдання фіксувати репозиторій, гілку, HEAD SHA, PR, виконані й пропущені тести, залежності, блокери й наступний крок.

## Очікуваний результат наступного етапу
Одна перевірена матриця **всіх гілок, PR, залежностей і рішень** та рекомендована послідовність інтеграції. До її затвердження — **жодних злиттів, архівацій, видалень або production-змін**.

Цей файл — план аудиту, а не твердження, що всі PR уже проаналізовано по diff чи що робочий production знайдено.
