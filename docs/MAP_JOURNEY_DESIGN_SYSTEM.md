# MARSHGO Map + Journey Design System — ТЗ і статус реалізації

Джерело: ТЗ власника продукту (жовтень 2026). Цей файл фіксує принципи та чесно показує, що вже є в коді.

## Принципи (обов'язкові)

1. **Задача, а не транспорт.** Користувач вводить A→B; система шукає реалістичні комбінації сегментів, порівнює, пропонує найкращі, веде Journey.
2. **Map Mode ≠ Mobility Layer.** Режим карти визначає *як* видно карту; шар мобільності — *що* на ній. Не робити режими «Прокат», «Самокати».
3. **Рівно три режими карти:** 2D, 3D (навігація), Супутник. Транспорт, метро, велосипеди тощо — це інформаційні шари поверх 2D, а не окремі карти. Активна навігація автоматично вмикає чистий 3D.
4. **Контекстна мобільність.** Показувати лише ті assets (велосипед, самокат, мопед, каршерінг), що реально скорочують Journey; кластеризація при віддаленні; не показувати pickup без drop-off.
5. **Одна дизайн-система**: єдині іконки, кольори за функцією (бренд — один акцент; зелений — доступно; помаранчевий — зміна; червоний — проблема; сірий — другорядне), єдина картка маршруту.
6. **Не обіцяти без даних.** Немає провайдера — немає пропозиції; стан «Скоро» чесно позначається.

## Модель даних Journey (цільова)

```
Journey
 ├── Segment: WALK | TRANSIT | CARPOOL | TAXI | BIKE | EBIKE | SCOOTER | MOPED | CARSHARING
 ├── Pickup / Dropoff
 ├── ETA, Price, Provider, Availability
```

Статус: серверний Journey Engine (`server/journey`) уже зберігає journeys із legs (`mode`, ціна, ETA, availability, provider_type, state) — міграція 020. Підтримуються режими COMMUNITY (carpool) і заглушки для інших.

## Статус реалізації

| Вимога ТЗ | Статус |
|---|---|
| 3 режими карти (2D / 3D / Супутник), без четвертого | **Є.** `MapLayerSwitch`; навігація вмикає 3D і повертає попередній режим після завершення |
| Інформаційні шари в 2D (метро, автобуси, трамваї, тролейбуси, зупинки, велосипеди, самокати, пункти прокату) | **Є.** MapLibre sources/layers, завантаження за viewport (bbox) і лише для ввімкнених шарів; за замовчуванням усе вимкнено; LOD за zoom (лінії від 10, транспорт від 11, прокат від 12, зупинки від 13); кластеризація мікромобільності; realtime-позиції оновлюються кожні 15 с лише поки шар увімкнено (вимкнення зупиняє опитування); кеш геометрії 6 год, позицій 10 с; gzip. Екран `/map` («Карта транспорту») із швидкими chips |
| Метро | **Шар є, даних немає:** відкритих GTFS метро для України не знайдено, перемикач сірий «немає даних» |
| Стилі Google / Apple / Waze | **Прибрано з інтерфейсу** (3 режими замінюють); токени стилю лишились у коді |
| Темна тема | **Є** (карта — інверсія фільтром; для Hybrid фільтр вимкнено) |
| Вибір точки на карті (як BlaBlaCar) | **Є** (пошук, публікація, заявка). Потрібен геокодер без ліміту |
| Групування видів транспорту | **Частково** — плиткова сітка; групи за макетом ще не зроблені |
| Intelligent / contextual mobility, rental pickup+drop-off | **Немає.** Потрібні провайдери (Bolt, Uber, Nextbike…) і модель assets із зонами повернення |
| Різні стилі сегментів на карті (пішки/транспорт) | **Немає**; зараз одна лінія маршруту |
| Layers control | **Частково:** одна кнопка «Шари» (шар карти + стиль). Фільтрів мобільності немає |
| **Mobility Control Center (Admin)** | **Частково:** реєстр провайдерів (міграція 029), додати / перевірити / увімкнути / вимкнути, статус health, журнал дій, адмін-роль, захист від SSRF. **GBFS:** повна перевірка й нормалізація в `MobilityAsset` (перевірено на живому фіді: 2781 ТЗ, 273 станції). Інші типи (GTFS, GTFS-RT, GOFS, REST…): лише перевірка доступності, валідатор не реалізовано |
| Імпорт даних провайдерів у БД, синхронізація за розкладом, force refresh/reimport, кеш | **Немає** (перевірка читає фід, але не зберігає активи) |
| Ключі API провайдерів (шифроване сховище, ротація) | **Немає** — лише публічні фіди |
| Ролі City Admin / Support / Analyst, 2FA | **Немає** (є лише admin і moderator) |
| Admin Map, Partner Portal, API Registry | **Немає** |
| Кластеризація маркерів | **Немає** (немає маркерів) |
| Transit: лінії, зупинки, пересадки | **Немає** — потрібен GTFS / провайдер |
| Bottom sheet (мобільний) / ліва панель (веб) | **Частково** (веб — окрема панель результатів; bottom sheet немає) |
| Passive matching водія | **Є** (навігація → збіги вздовж маршруту → пропозиція) |
| Live pickup + швидкі кнопки | **Частково** (rendezvous, статуси; швидкі кнопки «Я тут»/«Під'їжджаю» — перевірити) |
| Покрокова навігація з голосом | **Немає** — потрібен OSRM `steps` у контракті маршруту |
| Loading / error / empty / offline стани | **Частково** |
| Accessibility (VoiceOver, Dynamic Type) | **Частково** (aria-label на більшості кнопок; без аудиту) |

## Наступні кроки (за пріоритетом)

1. Покрокова навігація: `steps=true` у OSRM → контракт `RouteResult.steps` → збереження в сесії → UI + `speechSynthesis`.
2. Модель `MobilityAsset` + `MobilityProvider` (адаптери), зони drop-off, ціноутворення; перший провайдер для реального тесту.
3. Journey Results: картки «Найшвидше / Найдешевше / Мобільний / Carpool» зі сегментами 🚶→🚗→🚶 (дані вже в `journey_legs`).
4. Сегменти на карті різними стилями (пунктир пішки, суцільна авто).
5. Власний геокодер і транзитні дані (GTFS) для продакшну.

## Map layers API (2026-10-08)
`GET /api/v1/transport/layers` · `/transport/routes|stops|vehicles|micromobility?bbox=west,south,east,north&types=…` (потрібен вхід; bbox обмежений: маршрути/позиції ≤ 2°, зупинки ≤ 0,5°, мікромобільність ≤ 0,6°). Дані: GTFS (лінії з shapes або з послідовності зупинок найдовшого рейсу), GTFS-RT та JSON-фіди (позиції), GBFS (велосипеди, самокати, станції).

Ще не зроблено з ТЗ: картка транспорту з наступними зупинками й часом прибуття (потрібні TripUpdate/StopTimeUpdate), картка зупинки з прогнозом, анімація руху між оновленнями, multimodal routing, шари паркінгів/зарядок/ДТП, iOS-перевірка плавності на iPhone 15/16 Pro Max.
