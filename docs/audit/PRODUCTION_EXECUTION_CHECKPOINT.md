## Завершено в цьому фрагменті

1. У [production completion ТЗ](../PRODUCTION_COMPLETION_TZ_2026-10-18.md) додано обов’язковий цикл реалізації, перевірки, виправлення й переходу до наступного P0/P1, а також checkpoint для безпечного відновлення після переривання.
2. Server зіставляє provider-scoped GTFS ID маршруту/рейсу з сирими ID VehiclePositions; зберігає окремий provider stop ID для точки посадки.
3. Journey live API приймає `legId`, повертає точні напрямки статичної лінії та всі свіжі GPS-позиції її provider+route. Геометрію малюємо лише з `shapes.txt` GTFS; пряму між зупинками не видаємо за точну лінію. До трьох машин акцентуються тільки за збігом поточного trip, service date/route та прогресу до boarding stop. Невідомий напрямок або stale GPS не отримують статусу «наближається».
4. Site запитує live контекст після вибору сегмента, приховує інші етапи тільки на карті, малює обидва доступні напрямки приглушено, поверх лишає колір вибраного етапу; флот малюється одним GeoJSON-шаром із транспортними піктограмами. Якщо feed не має точної повної геометрії, UI прямо повідомляє, що лінію не домальовує. Камера не повторює наближення на кожному опитуванні.

## Наступні кроки без повторного аудиту

1. Додати/виконати ізольовану API integration перевірку `/api/v1/journeys/:id/live?legId=…` з фікстурою GTFS + GTFS-RT і перевірити реальну відповідь: всі свіжі машини обох напрямків, stale removal, максимум три доведені під’їзди, порожній/недоступний feed.
2. Виконати візуальну перевірку Site на справжньому або контрольованому фіді: вибрати автобус/маршрутку, перевірити line geometry, маркери, зникнення інших етапів із карти й збереження повного розкладу в панелі; зробити світлий і темний screenshot.
3. Перевірити показники provider health/rights у цільовому середовищі. Якщо Lviv provider не дає точного route/trip/stop progress, чітко лишити його непріоритетним/stale; не підміняти його моками.
4. Потім продовжити P0 двосторонню GPS-зустріч у Server/Site/iOS; перевірка лише unit-тестами її не закриває.
5. Підготувати staging exact-SHA, API/DB/Redis, smoke та rollback докази. Production traffic, destructive migration та App Store publish не робити без окремого підтвердження власника за раніше затвердженим правилом.

## Обмеження продовження

ТЗ не може тримати процес Codex активним після завершення turn, закриття сесії або сну комп’ютера. Перед завершенням активного turn оновити цей файл із новою фактичною SHA/гілкою, результатами й наступною конкретною дією; наступний запуск почати з цього checkpoint та актуального `git status`.
